Keeping the Referent in the DARK

An IoT operator wants a cloud model to answer questions about its logs. The question names an account, and the account is exactly the value that must not be sent. Every policy below is real: the prompts come from the same construction the paper uses, and the answers are what the reader actually returned on those prompts.

1. Why this is hard

An operator asks:

In the log above, which persona id is recorded for the account ACCT-f57fb0af0787?

The record that answers it carries that account on its identifying line. So the value that has to be hidden is also the handle the reader needs in order to know which record is being asked about. Hiding it removes the referent; keeping it forwards the secret.

That is the whole problem, and it is why redaction and compression fail in different directions rather than by different amounts. Neither is a weaker version of the other.

3. The same pattern at scale

DARK is the only row that reaches both 100% GIC and 0% leakage. It is not the highest F1: the uncompressed prompt scores 0.6081, and Quito-X reaches a statistically indistinguishable 0.4831 against our 0.4937. The claim is not that we compress better; it is that we are the only method that answers the question without forwarding the value.
