# Harness versions, and the two budget bugs

This note exists so that nobody re-introduces either bug, and so that the provenance of each harness
revision is on the record. It was written while the revisions were still being reconciled; the r1–r4
sources are not part of this snapshot (see [docs/status.md](../../docs/status.md)), but the failure
modes are, because they are the reason the budget guard is written the way it is.

## Which revision produced which result

| Revision | Role |
| --- | --- |
| `e2e_longctx.py` (r1) | first long-context harness; **its bytes in the shared tree are not trustworthy** — see below |
| `e2e_longctx_r2.py` | first revision that passes the real-tokenizer budget gate; authoritative for the r2-era results |
| `e2e_longctx_r3.py`, `r4.py` | incremental revisions (labelling, arm injection) |
| `e2e_longctx_r5full.py` | gold-free harness, the direct parent of `e2e_quad.py` |
| `e2e_quad.py` | **the harness in this repository**; regenerated byte-exactly by `../../analysis_quad4/make_e2e_quad.py` |

## Why the r1 bytes cannot be certified

The r1 file went through several writes whose byte provenance cannot be reconstructed: a delivery
report of 29,858 B, a copy into the repository, a bad patch, a recovery through a shell pipeline that
silently converted LF to CRLF, and a `git checkout` that returned 33,457 B including 709 CRLF pairs.
The hashes do not reconcile, and the most likely cause is a line-ending conversion applied more than
once — not a logic change. Consequence: **treat r1 as superseded, and do not cite its byte count as
provenance.** The r2 file was downloaded directly and its size and SHA-256 match the run report
bit for bit.

## Bug 1 — an off-by-one that the assertion caught (present in the original)

`drop_to_budget` used the **sum of per-unit token counts** as its accounting quantity, and its
docstring asserted that this sum is an upper bound on the length of the space-joined text.

That assertion is false: joining inserts a separator, and each separator can itself cost a token. On
one real case the guard fired:

```
RuntimeError: budget overshoot (silent overshoot is not allowed):
              budget_random ratio=0.75 got=5378 B=5377
```

Exactly one token over. **The harness's own hard assertion is what caught it.** Had the code been
written to warn and continue, the +1 would have entered the results silently — and it landed on
`budget_random`, the very arm used as the control.

## Bug 2 — the fix that made it worse (introduced during repair)

The first repair trimmed the tail of the drop order: "drop units from the end of `order` until the
joined text fits". But `order` was **designed to put the answer-bearing units last**, so this repair
deleted the answer first. Measured on a real case:

| ratio | B | sum before trim | real joined length | trim triggered? | gold answer still present? |
| --- | ---: | ---: | ---: | --- | --- |
| 0.25 | 2609 | 2507 | 2512 | no | yes |
| 0.50 | 5218 | 5216 | 5221 | **yes** | **no — deleted** |
| 0.75 | 7828 | 7811 | 7816 | no | yes |

The gold answer is present at 0.25, **gone** at 0.50, and back at 0.75: non-monotone, and silent.

**Correct repair (adopted in r2):** continue advancing a cursor along `order` while trimming, so the
discarded set is always a *prefix* of `order`. Nesting gives monotonicity, and monotonicity is what
makes "bigger budget implies weakly more retained" true by construction.

## Why the property test missed bug 2

The first repair was backed by 2,000 property trials with zero violations, and was declared verified.
Both of these were wrong:

- the fake token counter was `len(s.split())`, i.e. a **word proxy**, while the real gap comes from
  the tokenizer's separator cost;
- the trials asserted only `nt(text) <= B` and **never asserted that the gold answer survived**.

The test verified the invariant that had been in mind, not the one that mattered. This is the same
failure shape as three earlier episodes in this project, all of them "the quantity being counted is
not the quantity being asserted".

The original suite could not have caught it either: its counter was `len(re.findall(r'[A-Za-z0-9]+', s))`,
which is *additive* under space-joining, so the accounting gap is structurally invisible to it.

## The real-tokenizer gate (`test_budget_guard_real_tok.py`)

Run before a long GPU job; loads only the tokenizer, so it occupies no device memory:

```
R2 preflight rows=2016  misuse=0
R3 boundary_trials=2488  max_accounting_gap=1  old_violations=32  new_violations=0
R4 gold survival is non-decreasing in budget  ok
BUDGET_GUARD_ALL_PASS
```

**R3 is the key regression.** It enumerates every `B` at which a sum-based accounting would stop
exactly at the boundary — the only construction that can hit this gap. 32 old misuses become 0.

## What this means for anyone extending the harness

1. Measure with the real tokenizer. A word-count proxy cannot see separator cost.
2. Assert the property you care about (the answer survived), not a proxy for it.
3. Make the guard **raise**, never warn. A one-token overshoot on a control arm is exactly the kind of
   defect that survives review.
4. Keep the drop order monotone: trim a prefix, never an arbitrary subset.
