## 为什么

### r2 为什么可信

`e2e_longctx_r2.py` 是从集群 `$RD/e2e_longctx_r2.py` 直接下载的，**字节数与 sha256 都与运行 agent 的报告逐位吻合**（34,204 B / `b6a584f845b8816df5860fd166cbeb3ac1d411eea991c77d89eeb80b136188cf`）。它修掉了下面两个 bug，并通过了真实 tokenizer 门槛。

### `e2e_longctx.py` 为什么不能信

它在我手里经历了三次不一致的写入，**当前仓库副本的字节来源已无法担保**：

1. 构建方交付时报告 29,858 B（本机 `hpc\e2e_longctx.py`）。
2. 我把它复制进仓库并提交（`1079b04`）。
3. 我给它的 `drop_to_budget` 打了一个**错误补丁**并提交（`b75164a`）—— 该补丁本身引入了更严重的 bug，见下。
4. 我试图用 `git show … | Set-Content -Encoding UTF8` 恢复原版，**PowerShell 管道把 LF 转成 CRLF**，得到 32,042 B（提交 `b55698e`）—— 等于提交了一个被改坏字节的"原始版"。
5. 改用 `git checkout 1079b04 -- …` 恢复，得到 33,457 B 且含 709 个 CRLF —— 说明仓库里 `1079b04` 的那个 blob（远端 32,748 B）**本身就不是 29,858 B 的原始版**，即步骤 2 的复制已经改变了字节（很可能同样是 CRLF 转换）。

**根因**：本机 git 的 `core.autocrlf` 在工作区检出时做 LF→CRLF 转换，而我的几次复制/管道写入又各自叠加了一次转换。哈希对不上就是这个原因。

**要恢复真正的原始版**：请从集群 `$RD/e2e_longctx.py`（运行 agent 明确声明**没有覆盖**它，仍是 29,858 B 的原始件）直接下载，并以 sha256 登记。不要用本机工作区的副本反推。

## 两个 bug（供论文与后续引用）

### bug 1（原版就有的 off-by-one）

`drop_to_budget` 用"逐单元 token 数之和"当作记账量，并在 docstring 里断言它是空格拼接文本的上界。

**该断言是错的**：拼接会插入分隔空格，每个分隔符自身可能占一个 token。实测 `longctx-toolmem-needle-0003`：

```
RuntimeError: 预算突破（不允许静默超标）: … budget_random ratio=0.75 got=5378 B=5377
```

正好超 1。**这次是 harness 自己的硬断言把真实超标拦下来的** —— 若当初写成"打警告继续跑"，这个 +1 会静默进入结果表，而且恰好落在 `budget_random`，即我们用来做对照的那条臂。

### bug 2（我的修复引入，更危险）

我给的修法是"精确修剪时从 `order` **尾部往前**丢单元"。但 `order` 的设计**故意把含答案的单元排在最后** —— 所以这个修法等于**先删答案**。

运行 agent 在真实数据上量了出来（`longctx-toolmem_raw-needle-0002`）：

| ratio | B | 预剪后 sum | 真实 joined | trim 触发 | 金答案还在吗 |
|---|---|---|---|---|---|
| 0.25 | 2609 | 2507 | 2512 | 0 | ✅ |
| 0.50 | 5218 | 5216 | 5221 | **1** | **❌ 被删** |
| 0.75 | 7828 | 7811 | 7816 | 0 | ✅ |

**金答案在 0.25 存在、0.50 消失、0.75 又回来** —— 非单调，且静默。

**正确修法（r2 采用）**：精确修剪**沿 `order` 用游标继续前进**，使被丢弃集合始终是 `order` 的前缀（嵌套 ⇒ 单调）。

### 我的验证为什么没抓到 bug 2

我写了 2000 项性质测试、0 违反，然后宣布 "FIX VERIFIED"。但：

- `nt` 用的是**词级代理** `len(s.split())`，而真实缺口来自 tokenizer 的分隔符成本；
- 测试**只断言 `nt(text) <= B`，从未断言金答案是否存活**。

**我验证的是我脑子里想的那个不变量，不是真正重要的那个。** 这与本项目此前三次"计数量 ≠ 断言量"同源（`pairs_similarity` 数候选对却要互斥对、V2 的 `merged += 2` 与实际移除量不符、`drop_to_budget` 数 token 和却要文本长度）。

原测试套件也抓不到：其 `nt` 是 `len(re.findall(r'[A-Za-z0-9]+', s))`，**对空格拼接可加**，所以记账缺口在结构上对它不可见。

## 真实 tokenizer 门槛（`test_budget_guard_real_tok.py`）

在集群上先跑，只加载 tokenizer、不占显存：

```
R2 预检行数=2016  违规=0
R3 boundary_trials=2488  max_accounting_gap=1  old_violations=32  new_violations=0
R4 gold 存活随预算单调不减  ok
BUDGET_GUARD_ALL_PASS
```

**R3 是关键回归**：它穷举了 sum 记账恰好会停下的那些 B 值 —— 那是唯一能命中此缺口的构造。32 个旧违规 → 0。
