## 21.1 秩泄漏（rank leak）：真实存在，且修复免费

### 问题

`v4_router.Aliaser` 在未设 `PT_ALIAS_KEY` 时，按 `(type, value)` **升序**发放别名字母。
攻击者若知道该文档涉及的值集合（例如来自一次库泄露），把值排序后与
`[ACCOUNT-A]`、`[ACCOUNT-B]` … 一一对应，即可**完全逆推**。

**关键事实：此前所有主实验都未设该 key**，所以原报告的 `leak = 0`
是在带秩泄漏的分配下测得的。

### 量化（300 例 / 4,512 个别名）

| 防守设置 | 攻击命中率 |
|---|---:|
| 未设 `PT_ALIAS_KEY` | **100.0%**（4512/4512）|
| 设 `PT_ALIAS_KEY` | **19.1%**（864/4512）|

k=5 时随机猜中率即 20%，因此**设 key 后等同于随机**。

### 修复的代价（同 300 例，唯一变量是环境变量）

| 臂 | F1 无 key | F1 有 key | Δ |
|---|---:|---:|---:|
| full | 0.7200 | 0.7200 | +0.0000 |
| alias | 0.5800 | 0.5500 | −0.0300 |
| **alias_budget_link@0.5** | **0.9333** | **0.9333** | **+0.0000** |

主臂完全不受影响 → **修复免费**。

### 全量重跑（keyfull，2,728 例 × 21 臂 = 57,288 条）

| 臂 | ratio | F1（无 key）| F1（有 key）| Δ |
|---|---:|---:|---:|---:|
| full | — | 0.6079 | 0.6079 | +0.0000 |
| delete | — | 0.2889 | 0.2889 | +0.0000 |
| alias | — | 0.5256 | 0.5151 | −0.0106 |
| alias_budget | 0.50 | 0.3031 | 0.3196 | +0.0165 |
| **alias_budget_link** | **0.50** | **0.6372** | **0.6520** | **+0.0148** |

**自检信号：16 个不含别名的臂×预算组合 Δ 全部精确为 0.0000**，
证明 `PT_ALIAS_KEY` 只作用于别名发放，未污染其他结果。

### 配对检验（有 key，2,728 例，bootstrap 4,000 次）

```
abl@0.5 − full        +0.0441  [+0.0249,+0.0638]  win 459 lose 330
abl@0.5 − bcl@0.5     +0.0125  [+0.0003,+0.0244]  win 164 lose 130
abl@0.5 − ab@0.5      +0.3324  [+0.3141,+0.3507]  win 956 lose  26  ← link 增益
alias − full          −0.0928  [−0.1082,−0.0773]  win 126 lose 380
delete − full         −0.3190  [−0.3368,−0.3010]  win  38 lose 904
```

预算曲线峰值仍在 **0.20**（0.6870），与无 key 时（0.6888）基本一致
→ **最优工作点的结论不受修复影响**。

## 21.2 公开基准：LongBench（外部效度检验）

### 构造方式

- 数据：`THUDM/LongBench` 中的 3 个 QA 任务各 100 例 = **300 例**
  （`multifieldqa_en` / `qasper` / `hotpotqa`）
- **context / question / answers 完全保持 LongBench 原样**，不拼接不改写
- 仅在上下文末尾**追加**一段 `device log`，注入 15 个合成 PII 作为 canary
- 上下文长度：5,227 – 101,762 字符
- 文件：`data/public_lb.jsonl.gz`；构造脚本 `code/make_public_bench.py`

### 结果 A：原问题（测压缩组件）

| 方法 | 年份 | F1 | 泄漏 | ctx_tokens |
|---|---|---:|---:|---:|
| cpc_native | AAAI'25 | **0.4579** | 14.7% | 4,485 |
| cpc | AAAI'25 | 0.4515 | 15.3% | 4,507 |
| provence_native | ICLR'25 | 0.4374 | 22.7% | 3,649 |
| quito_x | EMNLP'25 | 0.4251 | 100% | 4,485 |
| ext_full | — | 0.4181 | 100% | 9,014 |
| **OURS @0.50** | 本文 | **0.4167** | **0%** | 4,474 |
| **Perception Compressor** | **NAACL'25** | **0.3772** | **84.0%** | 4,233 |
| llmlingua2 | ACL'24 | 0.3710 | 99.7% | 4,507 |

配对检验（同 300 例）：

```
我们 − 全上下文         −0.0007  [−0.0404,+0.0392]  完全持平
Perception − 全上下文   −0.0402  [−0.0805,−0.0002]  显著更差
Perception − cpc        −0.0743  [−0.1157,−0.0338]  显著更差
我们 − Perception       +0.0396  [−0.0022,+0.0810]  接近但未达显著
```

**结论：通用长上下文问答上，我们的压缩组件与不压缩统计等价，输给 CPC。**
这句话必须写进 limitation——**"压缩优于全上下文"仅在 Qwen2.5-7B 上成立**，
Mistral-7B 上方向相反（0.8433 vs 0.9133）。

### 结果 B / C：link 机制的有效检验

| 版本 | 构造 | 是否有效检验 link |
|---|---|---|
| Type A | LongBench 原问题 + 注入 PII | ❌ 问题不引用 PII，link 无事可做 |
| Type B | 问题引用账号，但 device 与 account **同一行** | ❌ 锚点单元已含答案，`protect_of` 无增量（300/300 `ctx_tokens` 相等）|
| **Type C** | **两跳：`account ACCT-X belongs to user U-Y` / `user U-Y operates device sensor-Z` 分属两行** | ✅ 锚点单元与答案单元分离 |

**Type C 结果（300 例，预算 0.5，有 key）：**

| 臂 | F1 | 泄漏 |
|---|---:|---:|
| full | 0.0967 | 100% |
| alias（仅别名）| 0.7044 | 0% |
| alias_budget（无 link）| 0.0733 | 0% |
| **alias_budget_link（有 link）** | **0.2000** | **0%** |

```
link − nolink = +0.1267  [+0.0789,+0.1756]  win 50 lose 11
两臂 ctx_tokens 相同：仅 9/300（Type B 是 300/300）
```

**结论：`link` 机制在公开上下文上显著有效，但前提是「锚点单元 ≠ 答案承载单元」。**
这解释了此前所有观察：自建集（多实体，账号与属性分离）→ +0.33；
LongBench 原问题 → 0；Type B（同行）→ 0；Type C（两跳分离）→ +0.1267。

> ⚠️ Type C 中 `full` 只有 0.0967 而 `alias` 高达 0.7044——仅做别名替换就让
> 两跳任务从几乎不可答变为可答。因此该任务的**绝对数值不宜直接引用**，
> 只能作为机制检验；配对比较（link vs nolink）仍然有效。

## 21.3 2025 基线：Perception Compressor（NAACL 2025 Findings）

### 接入方式：不改作者代码

`code/run_pc.py` 只做三件事：import 作者的模块，按 `main()` 的顺序调用三个函数，
写出本项目的 ext 口径。

```python
import PerceptionCompressor as PC                      # 源码未改动
idx = PC.get_rank_results(..., 'perception_compressor', 'after', ...)
retain, r, tgt = PC.budget_control(..., rate, tokenizer, ...)
ctx = PC.Semi_Guided_Iterative_Compression(retain, query, model, tokenizer, args, r=r)
```

作者模块 `import` 了三个本机缺失但**从未被调用**的库（`pynvml` / `seaborn` / `tiktoken`），
因此用 `code/pc_stubs/` 下的三个空壳模块顶上，**未修改运行环境**。

### 运行情况

| 项 | 值 |
|---|---|
| 压缩 | **300 / 300 例完成** |
| 平均压缩后长度 | 3,995 token（原文 8,513 → 约 47%）|
| 执行分区 | `prod`（CPU），96 路并行；GPU 分区排队 8 小时以上 |

### 须写入 limitation 的偏离

1. guiding questions 由本地 **Qwen2.5-7B** 生成（作者只发布 NQ 版，脚本未公开）
2. 上下文按段落切分为多 `ctx`（作者原数据是检索段落）
3. `compression_rate=2`（保留 50%），对齐本项目等预算协议
4. 作者 `budget_control` 在 `compression_rate=1` 时抛 `UnboundLocalError`，
   **无法提供不压缩对照**
5. 在 CPU 分区执行，未用作者的 GPU fp16 配置

### 其余 2025/2026 候选：逐个核查后不可用

| 候选 | 阻塞点 |
|---|---|
| AttnComp (AAAI'25) | 找到的仓库是另一篇论文（SWE agent 轨迹压缩）|
| 500xCompressor (ACL'25) | 输出 embedding token 而非文本 → 无法计算 canary 泄漏 |
| SCRL (IJCAI'25) | GigaWord checkpoint 未发布，需自训 |
| KIS (IJCAI'25) | 实现里 `self.gpt_tokenizer` 未定义；150 字符分块 → 300 例约 5.6 GPU·小时 |
| PCToolkit (IJCAI'25) | 工具箱，5 个压缩器 3 个与现有基线重复，不带来新增可比方法 |

## 21.4 论文表述的三处必要修正

1. **删除或限定**"压缩到 50% 优于全上下文"——仅 Qwen2.5-7B 成立，Mistral-7B 上相反
2. **"显著优于 Perception Compressor" → 改为"优于，未达统计显著"**（+0.0396，CI 跨 0）
3. **零泄漏的前提是 `PT_ALIAS_KEY` 已启用**（已验证免费）

可支撑的表述：

> 在**问题引用敏感标识符**的 PII-QA 任务上（自建集 2,728 例），本方法等预算下显著优于
> 全部已发表压缩基线（+0.154）且零泄漏；在通用长上下文问答（LongBench 300 例）上，
> 本方法在保持零泄漏的同时与全上下文统计等价，但不优于 CPC。
> 贡献是**隐私与效用的联合优势**，不是单纯的效用 SOTA。
