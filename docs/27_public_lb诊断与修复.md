# 27 · public_lb 三套基准的诊断与修复

## 27.1 三套基准的结构差异

| 基准 | 例数 | 有 `target_entity` | 有 `----- entry -----` | 问题含实体名 | 锚点与答案的单元距离 |
|---|---:|---:|---:|---:|---|
| `public_lb`（Type A）| 300 | **0** | 0 | **0** | 不适用 |
| `public_lb_typeb` | 300 | 300 | **0** | 300 | **0（同一句）** |
| `public_lb_typec` | 300 | 300 | **0** | 300 | **恒为 6 句** |

**关键：这两套都没有 `----- entry N -----` 记录块标记**（LongBench 段落本身不带这种结构）。

---

## 27.2 Type A：确实不适用（不是缺陷）

问题形如 *"What is the name of the most active fan club?"* —— **主题型问答，不含任何实体名**。

方法的核心是「问题点名的实体 → 保住它的记录块」，这里无对象可定位。
证据：`alias_budget` 与 `alias_budget_link` 结果完全相同（link 臂无任何增益）。

**结论**：Type A 属于论文的适用范围之外，应作为 scope 声明，而不是作为方法缺陷。

---

## 27.3 Type B：旧数字 0.31 的瓶颈是「上下文不足」，不是「答案丢失」

旧批次实测：

| 臂 | F1 | 答案在上下文 |
|---|---:|---:|
| `alias`（不压缩）| 0.9231 | 1.000 |
| `alias_budget` | **0.3100** | **1.000** |
| `alias_budget_link` | **0.3100** | **1.000** |

**答案 100% 在上下文里，模型仍然答错。**

原因：锚点那条记录同时含账号与答案（一条完整 JSON），但周围是 230 条同类记录。
**只保住那一条不够**——模型需要相邻记录作为判别依据，才能确认「哪一条才是目标账号」。

## 27.4 Type C：旧数字不可用（基线本身是错的）

| 臂 | F1 | 答案在上下文 |
|---|---:|---:|
| `alias` | 0.7044 | 1.000 |
| `full`（原始全文）| **0.0967** | **1.000** |
| `alias_budget_link` | 0.2000 | 1.000 |
| `alias_budget` | 0.0733 | 1.000 |

**原始全文 0.0967 比别名化的 0.7044 低 0.61，这不合理。**
最可能的原因是该批次中问题被别名化、而 `full` 臂的上下文是原文，两边对不上。

当前评测管线不会重现这一点：`question_for_arm` 只对 `ARMS_ALIAS = ['alias','alias_budget','alias_budget_link','quad4']` 里的臂改写问题，
`full` 拿到的是原始问题。**因此 Type C 的旧数字不能作为结论依据。**

## 27.5 修复：无记录块结构时的锚点句窗回退

原 `quad4` 用「锚点所在 entry」定位相关区域。没有 `----- entry -----` 标记时，
所有单元都落进同一个伪 entry（`-1`），导致**全部单元被判为相关 → 强制保留 = 整个上下文 = 2 倍预算 → `check_budget` 抛错**。

实测：Type B / Type C 上 **100/100 案例强制部分超预算，quad4 根本无法运行**。

### 改动（`code/longctx/e2e_quad.py`）

1. **模式判定**：若文本中不存在 `----- entry N -----` 标记，改用「锚点前后各 2 句」作为相关区域
2. **强制集合裁剪**：若强制保留部分本身超预算，按与锚点的距离从远到近裁掉，
   被裁的降级为可丢弃 —— 保证 `check_budget` 永不因超支抛错

### 模型无关验证（每个数据集 150 例）

| 数据集 | 模式 | 强制/预算 | 输出超预算 | 答案留存 | 泄漏 |
|---|---|---:|---:|---:|---:|
| `longctx_max` | entry 150/150 | 0.398 | 0/150 | **100%** | 0 |
| `public_lb`（Type A）| window 150/150 | 0.000 | 0/150 | 16.0% | 0 |
| `public_lb_typeb` | window 150/150 | 0.023 | 0/150 | **100%** | 0 |
| `public_lb_typec` | window 150/150 | 0.023 | 0/150 | **1.3%** | 0 |

**`longctx_max` 的行为完全不变**（entry 模式、强制 0.398、答案 100%），
所以 `docs/24` 里 2,728 例的结果仍然有效。

## 27.6 预期与局限

| 基准 | 预期 | 依据 |
|---|---|---|
| Type B | 明显改善 | 锚点与答案同句（距离 0），±2 句窗必然覆盖；且补充了判别用的相邻记录 |

## 27.9 两处预测需要更正（实测推翻）

### 更正一：Type C 没有失败

原预测「答案距锚点恒为 6 句，±2 句窗够不到，Type C 仍会失败」——**错**。

实测 `quad4` 在 Type C 上 `ans_in_ctx = 0.960`（答案在上下文里 96%），F1 0.6733。

原因：±2 句窗只贡献 1.3% 的答案留存，但**句窗之后还要按冗余度填充到 50% 预算**，答案单元在这一步被补回来了。所以最终答案留存是 96%，不是 1.3%。

**结论**：Type C 不是方法的失效场景，`quad4` 在此反而**大幅优于原始全文**（+0.5767）。

### 更正二：Type C 的 `full` 只有 0.0967 是真实值

原本怀疑是旧批次基线出错。实测在干净管线下 `full` 仍然是 **0.0967**（答案在文 1.000），而复现了旧值。

真实原因：Type C 的账号是长十六进制串，原始全文里 235 条相似记录，模型难以区分；
**别名化把它压缩成短而互异的 token（`[ACCOUNT-A]`、`[ACCOUNT-B]`…），反而使任务变简单**（`alias` 0.7078）。

即：Type C 上**别名化提升效用**，这是隐私与效用同向的有趣案例。

## 27.10 「别名 vs 删除」的三向验证

| 基准 | `quad4` − `quad4_del` | 判定 | 锚点是否为敏感值 |
|---|---:|---|---|
| Type A | +0.0013 | 不显著 | 无锚点 |
| Type B | **+0.7933** | 显著 | 是（账号）|
| Type C | **+0.6733** | 显著 | 是（账号）|

Type C 上 `quad4_del` 的 F1 = **0.0000**，而答案在文 0.963 —— **答案就在上下文里，但指代被抹掉了**，模型无法回答。
这是「敏感且相关这一格必须用别名、不能删除」最干净的实证。

## 27.11 发现一处实现不一致（待修正）

`quad4` 的预算填充方向与既有 `drop_to_budget` **相反**：

- `drop_to_budget`：按丢弃序**从前往后丢**直到低于预算 → 保留**最不冗余**的
- `quad4`：按丢弃序**从前往后加**直到达到预算 → 保留**最冗余**的

即 quad4 的填充方向是反的。实测在 Type B/C 上仍取得好成绩（因为答案单元恰好较冗余），
但这偏离了论文声明的「冗余度越高越先丢」规则，**应改为遍历 `reversed(drop_order)` 并重跑**。

修正前，上述 Type A/B/C 与 `longctx_max`、112 例的数字都基于「保留最冗余」这一非预期行为。
