## 3. 十二个组合方案

### 组 A · 路由机制（谁来决策）

**A1｜四象限硬路由**　`[基准方案]`
- **组成**：敏感度 × 任务相关性 → {删除 | 泛化 | 合并 | 保留}
- **依据**：mask 证明"敏感+无关→删除"双赢；PACT 的聚类对应"不敏感+无关→合并"
- **预期**：F1 持平，paraphrase 覆盖上扬
- **失败含义**：硬路由边界太锐 → 转 A2

**A2｜联合打分软路由**　`[改动最小，强烈推荐先做]`
- **组成**：单评分 `score = α·importance − β·sensitivity`，排序取 top-k
- **依据**：QUITO-X 本身就是"打分排序"（F1 51.87），**换成新评分即可插进现有 track，零架构改动**
- **预期**：与现有 harness 完全兼容，最快出数
- **失败含义**：若 α/β 怎么调都打不过 mask_quito_x → 说明单评分表达不了四象限

**A3｜查询条件化路由**
- **组成**：只对与当前 query 相关的敏感项做泛化，无关的直接删
- **依据**：QUITO-X 用 query 提升选择；此方案把 query 用到**隐私侧**（现有方法没人这么做）
- **预期**：相关敏感项被泛化而非删除 → 冲突场景下掉分更少
- **失败含义**：若 query 信号对隐私决策无帮助 → 退 A1

### 组 B · 顺序机制

**B1｜先压缩后判定（merge-then-judge）**
- **组成**：先按 `d_red` 激进聚类合并，再在合并结果上检测敏感残留，只对残留处泛化
- **依据**：`cpc` 无 mask 移除率已达 97.81% —— **压缩本身就会消灭大部分表面形式**，先压缩可减少需要泛化的位置
- **预期**：泛化调用次数下降，延迟降低
- **失败含义**：若残留位置反而更多 → 说明聚类放大了敏感项（危险信号）

**B2｜三层级联（粗到细）**
- **组成**：正则扫已知格式 → 嵌入聚类处理语义残留 → 对抗校验兜底（见 E1）
- **依据**：动机实验显示正则 100% / 变体 9.1%，**两层解决的是不同分布**
- **预期**：paraphrase 覆盖率是三个机制里最高
- **失败含义**：若第二层贡献 ≈ 0 → 语义残留本来就少

**B3｜级联预算重分配**
- **组成**：去敏省下的 token 预算还给任务相关证据
- **依据**：mask 的 ΔF1 **26/32 为正**（删无关键反而涨分），说明预算可回收
- **预期**：同预算下 F1 不降
- **失败含义**：预算不是瓶颈，选择质量才是

### 组 C · 粒度与结构

**C1｜层级多分辨率聚类**　`[直接对治一个已验证的矛盾]`
- **组成**：句子级粗聚（保流畅）+ token 级细聚（保隐私）
- **依据**：数据里 **`provence` 移除率仅 66.00% vs `quito_x`/`dac` 更高** —— 粒度粗则敏感跨度整体存活；粒度细则丢流畅
- **预期**：同时拿到粒度粗的效用与粒度细的隐私
- **失败含义**：两者不可兼得 → 必须选边

**C2｜簇内差异保持**
- **组成**：合并时保留"差异方向"（时间先后、状态翻转），只丢幅值
- **依据**：项目自己的 2×2 诊断——**body 替换会改变预算选择，而顺序单独改变不会**，说明顺序/结构本身承载信息
- **预期**：合并后保留可推理的方向信息
- **失败含义**：模型不需要方向信息

**C3｜跨视图一致性去敏**
- **组成**：同一事件生成多个等价表示（改写/摘要/结构化），**只有全部表示都不泄漏才允许入链**
- **依据**：yf-research 的"竞争假说"思路；也直接对治 40% 隐形泄漏
- **预期**：隐形泄漏显著下降（用一致性替代单次判定）
- **失败含义**：一致性判据过严 → 大量证据被误杀

### 组 D · 信息保留方式

**D1｜可逆别名映射（reversible aliasing）**　`[原型注入的强版本]`
- **组成**：敏感值 → **稳定别名**（同一值永远同一别名），模型可在别名上推理（"同一账户"），答案侧再还原
- **依据**：`cpc` 的干净度来自"重写"；别名是比 `[REDACTED]` 信息量高得多的轻量重写
- **预期**：含敏感项的推理题掉分最少
- **失败含义**：模型不需要实体同一性 → 退回普通泛化

**D2｜原型注入**
- **组成**：`ACCT-fe9d…` → `[账户类别A]` 而非 `[REDACTED]`
- **依据**：同 D1，但别名不保证稳定
- **预期**：比纯删除保留更多可用信息
- **失败含义**：与 `[REDACTED]` 无差异 → 删除就够

### 组 E · 校验闭环

**E1｜对抗再识别校验**　`[唯一直接打击"隐形泄漏"的方案]`
- **组成**：本地小模型尝试从压缩结果**反推被删的敏感值**；能推出就打回重做
- **依据**：动机实验的 40% 隐形泄漏 —— 现有指标测不出来，**需要一个独立攻击者视角**
- **预期**：把"指标看不见的泄漏"变成"可测量的泄漏"
- **失败含义**：本地小模型推不出来，但更强模型能 → 需要换更强攻击者（诚实标注）

### 组 F · 集成与预算

**F1｜多压缩器按内容路由**
- **组成**：按片段类型分派——事实密集段给抽取型（`quito_x`），冗余段给抽象型（`cpc`）
- **依据**：**不同数据集的最优压缩器不同**：`cpc` 赢 SQuAD 两模型全档位（Qwen 86.91 档位 84.62 / Llama 54.86），而 `provence`/`quito_x` 赢 HotpotQA（Qwen 53.79 / Llama 31.39）→ **内容类型决定最优压缩器**
- **预期**：在四格上都接近各自最优
- **失败含义**：路由判据不可靠 → 说明是数据集层面而非内容层面的差异

**F2｜敏感度感知的预算分配**
- **组成**：不同 token 拿不同预算份额——敏感跨度允许膨胀（泛化需更多 token），冗余跨度归零，任务相关跨度按保护额度
- **依据**：`mask_cpc` 实际保留率只有 **0.4067–0.4851**（低于 0.50 目标）说明预算分配已经在暗中发生；`provence` native 掉到 **0.11903** 说明分配失控
- **预期**：同预算下效用—隐私同时改善
- **失败含义**：预算分配不是杠杆

## 4. 推荐主攻（三个，覆盖不同风险）

| 优先级 | 方案 | 理由 | 风险 |
|---|---|---|---|
| **P0** | **A2 联合打分软路由** | 零架构改动，能直接插进现有 11 track harness，**最快出数** | 单评分可能表达不了四象限 |
| **P0** | **B2 三层级联** | 正则与语义两层分布不同（100% vs 9.1%），**最可能真正提高 paraphrase 覆盖** | 第二层增益可能很小 |
| **P1** | **E1 对抗再识别校验** | **唯一直接对治 40% 隐形泄漏**，而且它本身就是一个可发表的测量贡献 | 攻击者强度决定结论 |

**A2 出工程速度，B2 出主卖点，E1 出测量可信度。** 三条并行，互不阻塞。

| 消融 | 去掉什么 | 若结果说明 |

| **随机合并（同预算）** | 聚类本身 | **聚类不是机制** |

## 6. 跨数据集验证计划（对应"从不同数据集抽样本"）

**本地已有数据源**（`external/` 与 `research/`）：

| 数据集 | 性质 | 与本任务的关系 |
|---|---|---|
| SQuAD 1.1 | 单跳问答 | 已有基线（四格中两格） |
| HotpotQA distractor | 多跳问答 | 已有基线（另两格） |
| **PrivacyLens** | 隐私专门基准 | **真隐私语义，不是合成标识符** ← 补上最大短板 |
| **PISanitizer** | PII 净化 | 现成的去敏对照 |
| **PEC-Home** | 家庭助理 | 接近 IoT |
| **SimuHome** | IoT 设备控制 | **最接近 IoT**，有历史依赖 |
| **AgentDojo banking** | 工具调用 | 敏感数据 + 动作 |
| **toolmem_conversation.jsonl** (31.8 MB) | 工具调用记忆 | **日志形态**，最像真实 IoT 日志 |

**抽样设计**：每个来源抽 96 例（对齐 batch1 规模），**canonical + 3 类 paraphrase 变体**，冻结为 `.jsonl` + sha256，登记后不再改。

**资源分工**（依据 2026-10-15 实测）：

| 阶段 | 需要什么 | 放哪 |
|---|---|---|
| 抽样 + 变体注入 + 冻结 | 纯 CPU，无模型 | **本地** 或 Madar `prod` |
| 离线聚类可行性（字符/词级代理） | 纯 CPU | Madar `prod`（现有 22464 空闲 CPU） |
| 嵌入提取 + 真聚类 | 1×GPU | Madar `gpu`（**只剩 1 节点，8×H200，需排队**） |
| 压缩 + 推理 + 评分 | 1×GPU | 同上 |

> ⚠️ Madar `gpu` 分区现仅 1 节点且已有作业运行中（`tc-evalfull`）。**GPU 作业要排队，CPU 作业立刻能上**——所以先把 CPU 部分全部推完。
