### ❌ 结论 2：叠聚类**掉分**
`qtx_cluster` vs `qtx`：SQuAD **−0.96**、HotpotQA **−6.03**，合计 **−3.50 F1**，换来约 **15% token 节省**。

**这是一笔亏本买卖**：为省 15% 的 token 掉了 3.5 分。

### ⚠️ 结论 3：聚类仍**优于随机合并**，但不一致
在**相近的削减幅度**下：

| 数据集 | 聚类 F1 | 随机 F1 | 聚类 token | 随机 token |

- **HotpotQA：聚类反而更差**（−2.83pp）✗
- → **机制有效但不稳定，不能作为主贡献。**

## 3. 🔴 最重要的发现（战略级）

**`mask_quito_x` 用一半 token，只掉了 0.75 分。**

| | token | F1 |
|---|---:|---:|
| `full`（不压缩） | 817.4 | 72.35 |
| `qtx`（50% 预算） | **408.5（正好 50.0%）** | 71.60 |
| 差距 | **省 50%** | **−0.75 pp** |

**也就是说：在 SQuAD + HotpotQA 上，"压缩"这个问题已经被 QUITO-X 基本解决了。**

推论非常硬：

1. **F1 上无空间可赢** —— 天花板就在 0.75 分以内，任何进一步压缩都必然掉分（v3 已实测：掉 3.5 分）。
2. **"更准的压缩算法"这条赛道，在这两个数据集上是死的。**
3. 我前面测出的"聚类 +7~8 分"是**在弱选择器上**的增益；一旦选择器够强（QUITO-X），**增益就被吃掉了**。

## 4. 所以贡献必须换地方

| 不能再作为主线 | 应该作为主线 |
|---|---|
| ❌ "更准/更省的压缩算法"（天花板 0.75 分） | ✅ **隐私覆盖**：改述/无格式敏感内容（正则 9.1%，见 V1） |
| ❌ "聚类在 SQuAD/HotpotQA 上更好" | ✅ **冲突消解**：敏感且任务相关时怎么办（现零覆盖） |
| ❌ 靠 F1 赢 | ✅ **同 F1 下的隐私与延迟**，或**真正需要压缩的场景**（IoT 行动历史 / 长工具链） |

**关键提醒**：SQuAD/HotpotQA 是**单跳/多跳阅读理解**，上下文短（800–1400 token），压缩本来就没多少油水。**你的 IoT/Agent 场景上下文长得多**（SimuHome 系统提示+工具表就 2,791 token），**那里压缩才有意义** —— 也才是该测的地方。
