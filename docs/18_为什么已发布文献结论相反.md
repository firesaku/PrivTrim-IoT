# 18 · 为什么已发布文献会得出"压缩对隐私与效用都无害"

> 2026-10-17 ｜ 发现方式：核对 batch1 已发布基准的**结构**，而非它的结论
> 性质：这解释了上一批工作的结论为什么与我们相反，并且**不需要否定他们的实验**

---

## 1. 已发布基准的形态

`PROTOCOL.md` 写明：SQuAD 1.1 dev，最多 96 题，**与原先相同的虚构邮箱/电话/账号注入方式，
位置前中后轮换**。实测 schema：

```
cases.json[i]  keys: answers, canaries, canary_position, context, id,
                     original_tokens, provence_estimated_tokens,
                     question, source_context, title
```

即 `context = 注入的隐私记录（前导）+ source_context（SQuAD 段落）`，
`question` 是 **SQuAD 的问题**。

## 2. 实测：可查询对象与需保护对象完全不相交

| 检查（96 例，288 个 canary） | 结果 |
|---|---|
| 问题里含 canary 值 | **0/96** |
| 答案文本含 canary 值 | **0/96** |
| canary 出现在 `source_context`（被问的段落）里 | **0/96** |
| 有 ≥1 个 canary 的案例 | 96/96 |

**所以在这个基准里，问题问的东西（SQuAD 事实）与需要脱敏的东西（注入记录）是两套
互不相干的文本。** 四象限里"**敏感且相关**"那一格 —— 答案本身要求使用必须被保护的值 ——
**在设计上就不存在**。

## 3. 这个设计后果，在他们自己的数字里看得见

已发布结果（96 例，预算 0.5，`matched` 轨；`pin_full` = 输入里完整敏感值被去除的比例）：

| 方法 | F1 | retention | pin_full |
|---|---:|---:|---:|
| `full`（不压缩） | 0.8444 | 1.000 | 0.000 |
| **`quito_x`** | **0.8574** | 0.499 | 0.451 |
| `cpc` | 0.7636 | 0.499 | 0.986 |
| **`mask_llmlingua2`**（脱敏+压缩） | **0.7507** | 0.499 | **1.000** |
| `provence` | 0.6849 | 0.499 | 0.601 |
| `llmlingua2` | 0.6747 | 0.499 | 0.417 |
| `dac` | 0.4647 | 0.499 | 1.000 |

两个观察，都能用"可查询对象与需保护对象不相交"解释：

1. **`mask_llmlingua2` 把输入里的敏感值 100% 去掉了（`pin_full = 1.000`），F1 仍有 0.7507**，
   相对 `full` 只掉 11%。因为答案在 SQuAD 段落里，脱敏前导根本不碰它。
2. **`quito_x` 在 50% 预算下 F1 = 0.8574，反超不压缩的 0.8444。**
   因为那段隐私前导在这个任务里**纯粹是干扰**，丢掉它反而帮了模型。

## 4. 同一个方法，在两个基准上

| | 已发布基准（96 例 SQuAD+注入） | 我们的多实体案例（40 例） |
|---|---:|---:|
| `full` | 0.8444 | 0.6083 |
| **`mask_llmlingua2`** | **0.7507**（相对 −11%） | **0.0000**（相对 −100%） |
| `llmlingua2` | 0.6747（相对 −20%） | 0.3417（相对 −44%） |
| `provence` | 0.6849（相对 −19%） | 0.4750（相对 −22%） |
| 可查询对象 = 敏感对象 | **从不**（0/96） | **总是**（40/40 问题点名实体） |

**同一类任务设定、同一个方法，失败在已发布的设计里看不见，在我们的设计里是 0.0000**
（相对崩塌 100%）。

> 注意口径：这是**两个不同基准**，绝对 F1 不可直接比。可比的是"同一方法相对 `full` 的
> 退化幅度"，以及结构性的"问题是否指向敏感值"。

## 5. 这对论文意味着什么

不是"他们做错了"，而是**他们的基准无法表达那一格**。所以：

- 他们报"压缩对隐私与效用都基本无害"，**在他们的设定下是正确的**——因为两个轴在
  设计上就是正交的；
- 我们的贡献不是推翻它，而是指出：**当把"被查询的对象"设成"必须保护的对象"时，
  结论反转**，而且反转的机制是明确的（冗余度信号与实体标识冲突，实测
  `budget_cluster` 在 40/40 个案例里删掉被查询实体却留着答案）。

这同时给了论文一个**干净的问题陈述**：

> 现有隐私-效用评测把"敏感"与"相关"当作两个独立的文本集合；
> 而真实 IoT 日志查询里，被查询的标识符**就是**敏感值。
> 我们构造并度量了这一格。
