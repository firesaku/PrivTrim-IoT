# 失败项与不确定项

> 本文档把**被证否的想法**、**我自己的错误**、以及**尚不确定的事情**单独列出来。
> 目的是：让这些内容不会被无意中写进论文。

## 第一部分：已验证不成立的想法（11 条）

### F1. 「做一个全新的压缩算法」❌
- **原想法**：新机制/新算法才像研究，应该自研一个压缩器。
- **为什么被否**：E2E v3 实测 —— `mask_quito_x` 在 **50% 预算**下，用**正好一半的 token**（408.5 vs 817.4）只比不压缩低 **0.75 分**（71.60 vs 72.35）。
- **含义**：这条赛道上 F1 天花板只有 0.75 分，新算法**没有空间可赢**。
- **证据**：`docs/analysis/E2E3_RESULTS.md`

### F2. 「用 PACT 原样的距离有界聚类就能解决」❌
- **原想法**：PACT 在视觉上有效，搬过来加上相似度下界 + 簇大小上限即可。
- **实测**：`bound_emb`（τ=0.75，簇≤4）→ mix_sens **0.0%** 但 `hit_answer` **5.1%**（比不加约束的 4.0% **还高**）。
- **含义**：**距离有界只保隐私、不保效用**。效用必须靠重要性约束 —— 这恰好是相对 PACT 的增量所在。
- **证据**：`results/reports/v3_bound_report.txt`

### F3. 「token 级会比句子级更好」❌
- **原想法**：项目数据里细粒度方法移除率更高，且 QUITO-X 是 token 级。
- **实测**：句子级 F1 **50.81** vs token 级 **45.85**（合计）；SQuAD **60.63** vs **59.09**。
- **含义**：16-token 窗口重建后文本碎片化，伤流畅度。**粒度不是越大越好也不是越小越好。**
- **证据**：`results/reports/e2e2_report.txt`

### F4. 「粒度是主要瓶颈」❌
- **原想法**：落后基线 27pp，先怀疑是句子级取舍太粗。
- **实测**：`mask_quito_x` 保住 full 的 **98.2%**（SQuAD 87.94/89.53），我的最好臂只保住 **67.7%**（60.63/89.53）。
- **含义**：**主因是选择器质量，不是粒度。** QUITO-X 的 token 打分（flan-T5 + query）精准得多。
- **证据**：`results/reports/join_report.txt`

### F5. 「把聚类叠到强选择器上能提升」❌
- **原想法**：聚类在弱选择器上有 +7~8pp 增益，叠到强选择器上应该也涨。
- **实测**：`qtx_cluster` vs `qtx`：SQuAD **−0.96pp**、HotpotQA **−6.03pp**、合计 **−3.50pp**。
- **含义**：**增益被强选择器完全吸收。** 选择器够强时，合并冗余反而丢信息。
- **证据**：`docs/analysis/E2E3_RESULTS.md`

### F6. 「叠聚类能省 token 而几乎不掉分」❌
- **实测**：省 **15.4%** token（408.5→345.6）但掉 **3.5pp F1**。
- **含义**：比例失衡 —— 为省 15% 的 token 掉 3.5 分，**不划算**。
- **证据**：同上

### F7. 「<CLUSTER> `gpu` 分区能很快拿到卡」❌
- **实测**：`squeue --start` 显示预计 **23:08**（提交时 17:08）→ **需等约 6 小时**。原因是本账号近期 GPU 用量把 fairshare 压低。
- **证据**：`docs/05_HPC运行记录.md`

### F8. 「<CLUSTER> `interactive` 分区可绕过排队」❌
- **实测**：提交后 `reason=(PartitionConfig)`；`scontrol show partition interactive` 显示 **`AllowAccounts=rcadmin`**，本项目账号 `<SLURM_ACCOUNT>` 不在允许列表内。
- **证据**：同上

### F9. 「正则漏删率 12.35%」❌ —— **我自己的错误**
- **经过**：全语料首次运行报 `redact_miss = 12.35%`，看起来像个重大发现。
- **诊断**（作业 1444040）：打印命中规则计数与样本上下文后证明是**我的启发式 bug** —— 数字段检查（本意用于电话）被应用到**所有类型**，账号 hex marker 抽出的"数字段"退化成单字符（如 `"1"`、`"963"`），在任意文本里都能匹配。证据：`variant_substr` 与 `tokenset` 规则**一次都没命中**；所有抽样上下文中标识符都已正确 `[REDACTED]`。
- **修正后真值**：**1.14%**。
- **含义**：**如果不做这一步诊断，会把一个 bug 当成发现报出去。**
- **证据**：`results/reports/v1_report.txt` vs `v1fix_report.txt` vs `v1b_report.txt`

### F10. 「SQuAD 的 answers 是字符串列表」❌ —— **我自己的错误**
- **经过**：首次端到端运行（作业 10598862）**EM 全部为 0.00%**，而 F1 有 30–50%。
- **诊断**：SQuAD 的 `answers` 是 `[{'text': ..., 'answer_start': ...}]` **字典列表**；我用 `str(x)` 把字典变成了字符串，金标准错误 → EM 恒 0。F1 仍有 ~50% 是因为**那个字典字符串里含答案原文**，给了 F1 一个假信号。
- **修正**：新增 `gold_texts()` 取 `x['text']`。
- **含义**：**5000 次生成的数字全部作废，重跑。** 如果不查，会把废数字当结果报出去。
- **证据**：`results/logs/e2ea-10598862.err`

### F11. 「证据闭包（关联保留）能提升安全完成率」❌（项目既有结论）
- **实测**（项目既有）：闭包 vs 简单元数据排序 **10+ 次独立复现全部打平**。
- **含义**：本项目主线假设之一已被证否。
- **证据**：项目 `docs/发表目标与证据台账.md`、`benchmarks/history_compression_dev_v1/RESULTS.md`

## 第二部分：部分成立 / 依赖条件的想法（6 条）

### P1. 「隐私护栏 `d_sens` 是必需的」⚠️ —— **我中途推翻过自己一次**
- **初判**（句子级，作业 1444036 的 `guard`/`scatter` 配置）：`cons_emb ≡ sim_emb`，簇数与三个指标**完全相同** → 判定"护栏冗余，一次都没触发"。
- **改判**（补跑 `gran` 配置，作业 1444045，**200 字符窗**）：`cons_imp_emb` 明显优于 `imp_emb`（mix **0.0%** vs 0.7–1.3%；fuse **0.0%** vs 0.2–0.6%）。
- **原因**：200 字符窗可以同时覆盖 2–3 个敏感项，句子不会。
- **教训**：**少跑一个粒度配置，我就会把错的结论写进论文。**
- **证据**：`results/reports/v3_guard_report.txt` + `v3_gran_report.txt`

### P2. 「聚类在强选择器上也优于随机合并」⚠️
- SQuAD：聚类 **86.58** vs 随机 81.15（且 token 更少）→ **+5.43pp** ✓
- HotpotQA：聚类 49.63 vs 随机 **52.46** → **−2.83pp** ✗
- **含义**：机制有效但**不稳定**，不能作为主贡献。
- **证据**：`results/reports/e2e3_report.txt`

### P3. 「隐私过滤几乎免费」⚠️
- **成立**：端到端 3 次独立实验均 ≤0.4pp（SQuAD −0.39、HotpotQA −0.23、v3 −0.25）。
- **但太弱**：正则脱敏本身不是新东西，不足以独立支撑贡献。只能作为**前置条件**或**附带收益**。
- **证据**：`docs/analysis/E2E_RESULTS.md`、`E2E2_RESULTS.md`、`E2E3_RESULTS.md`

### P4. 「现有隐私指标存在看不见的泄漏盲区」⚠️ —— **需严格区分两种说法**
- **语料本身**：`blind_spot = 0.00%`（因为那批语料**只含规范格式**）→ 原版检查器在该语料上是**正确的**。
- **反事实推演**：在**生成的 600 个改述变体**上，原版检查器看不见 40%。
- **含义**：这两个数字**必须分开表述**。说"现有指标有 40% 盲区"是**错的**；正确说法是"若输入含改述，原版指标将看不见其中 40%"。
- **证据**：`docs/analysis/paraphrase_probe_SUMMARY.txt` + `results/reports/v1fix_report.txt`

### P5. 「接口守卫能提升安全性」⚠️（项目既有）
- direct 界面 61/64 → 加守卫 **64/64**（修 3 例）
- **但**：加守卫后"更好接口"的收益变成**恰好 +0.00pp**（守卫吸收了接口增益）
- **证据**：项目 `benchmarks/strong_planner_analysis_v2/RESULTS.md`

### P6. 「目标接口修复能大幅提升」✅（项目既有，唯一强正机制）
- Qwen2.5-7B：安全完成 47/64 vs 24/64；配对 **+31.25pp [+18.75, +43.75]**（CI 不含 0）
- 这是能力线里**唯一区间不含 0** 的正机制
- **证据**：项目 `benchmarks/capability_v2/RESULTS.md`

## 第三部分：尚不确定的事项

### U1. 冲突场景（敏感 + 任务相关）完全没有数据
- 现有语料中敏感项**永远任务无关**（项目源码自述：`artificial identifiers are task-irrelevant; no privacy/utility conflict tested`）。
- 所以 **A5（冲突消解）无法验证** —— 必须先造数据。
- **这是当前最大的空白，也是唯一没人做过的格子。**

### U2. 换到长上下文场景后会怎样
- SQuAD/HotpotQA 上下文只有 800–1400 token，压缩无油水（50% 预算只掉 0.75 分）。
- 长上下文场景（toolmem / SimuHome / AgentDojo）**尚未实测**。
- 预期：那里 QUITO-X 不可能只掉 0.75 分，压缩空间真实存在 —— **但这是预期，不是结论**。

### U3. 聚类增益能否迁移到其他模型 / 其他数据集
- 只在 Qwen2.5-7B 上验证过；只在 7 个数据集上验证过。
- Llama-3.2-1B 表现明显更差（项目既有数据：90/92 条件更差），但未在我的臂上测。

### U4. `mask_quito_x` 存储文本与当时评分文本是否严格一致
- 我用他们的 `jobs.payload.matched.text` 复现，误差 ≤1 分（87.54 vs 87.94；55.66 vs 56.62）。
- 但严格说这是**间接证据**；未逐字节核对。

### U5. FP16 (V100) vs BF16 的数值影响
- 基线原本在 A6000/H200 上 BF16 跑；我在 V100 上跑 FP16。
- 我的 `full` 臂复现到 89.53 / 55.30，与基线 `full` 同量级 → 影响应小，但未做同硬件对照。

### U6. 隐私指标的改造尚未执行
- `joint_fragment` 是调和平均（导师明确反对）→ 尚未拆成三指标
- `privacy_lower_all` / `privacy_upper_all` 是假区间（184/184 行等于 `pin_fragment`）→ 尚未改
- `pout_fragment` 无区分力（127/184 = 1.0）→ 尚未替换
