# 07 · 代码复核与审计

> 2026-10-16 ｜ 目的：回答"**代码有没有真的做到我们宣称的事**"
> 方法：GLM 多 agent 审计（27 个 agent，三阶段）＋ 独立复算（重跑代码、核对原始 JSON）
> 结论一句话：**管线本身可复现且可信，但两处"臂未对齐"使两个头条结论的措辞超出证据允许的范围。**

## 1. 为什么要做这件事

前面 37 条想法里，**29% 被实测证否，其中 3 条是自身错误**（`docs/03_失败与不确定.md`）。这些错误有一个共同特征：**代码做的事 ≠ 我们以为代码做的事**。所以本轮不新增实验，专门审"声明与实现是否一致"。

审计分三阶段：

| 阶段 | 做什么 | 数量 |
|---|---|---:|
| 1 | 逐脚本审计：给每个脚本写明"预期意图"，让模型读代码判断是否忠实实现 | 15 |
| 2 | 专项审计：融合/叠加是否真融合、消融是否干净、四象限路由器是否真存在 | 3 |
| 3 | **对抗复核**：另一模型去读原始代码，试图**推翻**前一轮提出的每条指控 | 9 |

第三阶段是必须的 —— 见 §5，它挡掉了若干误报。

## 2. 已独立复核证实（我亲自重跑过）

### 2.1 🔴 V2 可行性实验的三个臂不在同一压缩预算上

**这是本轮最重要的发现。**

`v2c_feasibility.py` 在同一个 `ratio` 下比较三个臂，三个指标（`hit_answer` / `mix_sens` / `fuse_2sec`）都是**按簇算的比率**。比率可比的前提是三臂的**实际合并量相等**。它们不相等：

| ratio | similarity 簇数 | random_adjacent | random_far | 随机÷相似 |
|---:|---:|---:|---:|---:|
| 0.125 | 883 | 1011 | 1006 | 1.14× |
| 0.25 | 1376 | 1950 | 1950 | 1.42× |
| **0.5** | **2143** | **3926** | **3883** | **1.83×** |

（上表为我本地重跑 `code/v2c_feasibility.py` 全量 494 例的结果；已发布的 `v2c_cells.json` 为 885 / 1376 / 2143 —— 9 格中 6 格逐位相同，相似度臂差 ≤2，属 `argsort` 并列打破的浮点噪声。**即：管线本身完全可复现。**）

**根因（代码位置）**：`pairs_similarity()`（L73-83）从全局相似度排序里取前 `target/2` 对，**但不记录 unit 是否已被占用**；高相似度的对会围绕少数"枢纽"unit 大量重叠，随后 `make_clusters()`（L60-63）用 `used` 过滤把重叠对**直接丢弃且不回填**。而 `pairs_random()` 配对的是 `idx[k]` 与 `idx[k+1]`，天然互斥、从不冲突。于是相似度臂系统性欠合并，且缺口随 ratio 增大。

**影响**：

- `mix_sens` 的 **0.0% vs 15.3–18.8%** 这个招牌结论**方向很可能是真的** —— 在最接近对齐的 0.125 档（仅差 1.14×）差距已是 1.8% vs 17.0%。
- 但 **0.25 / 0.5 两档的效应量被夸大到最多 2 倍**，因为随机臂在那里合并了两倍的内容。
- **"聚类是机制不是装饰，可以放心投入实现"这句结论，其定量证据需要重跑后才能成立。**

**复现方式**（已收进仓库，退出码即门禁）：

```bash
$PY code/verify/check_merge_budget.py --samples data/frozen_samples.jsonl \
     --v2c code/v2c_feasibility.py --ratios 0.125,0.25,0.5
# → ratio=0.500  achieved only 45.3% of requested merges
# → VERDICT: FAIL   (exit 1)
```

**修复**：把贪心从"取满 `target/2` 个**候选对**"改成"沿排序表继续扫，直到凑满 `target/2` 个**互斥对**"（标准贪心匹配），然后重跑三档。

> 附带发现：`v2b_feasibility.py` 是同一个 bug 的更早版本（0.5 档 sim 2143 vs random 3708），`v2c` 逐字继承。属**同一根因**，不是两个独立问题。

### 2.2 🔴 E2E v3 的"叠加"实验无法支撑"聚类被强选择器吸收"

E2E3 的四个臂与实测 token：

| 臂 | 上下文 token | F1 | 相对 qtx |
|---|---:|---:|---|
| `full` | 817.4 | 72.35 | — |
| `qtx`（基线，50% 预算） | 408.5 | 71.60 | — |
| `qtx_cluster` | **345.6** | 68.10 | −15.4% token / −3.50 F1 |
| `qtx_random` | 371.7 | 66.80 | −9.0% token / −4.80 F1 |

代码（`e2e3.py` L242-259）：所有聚类臂的输入都是 DB 里 `mask_quito_x@0.5` 的**已发布压缩文本**，再在其上继续合并。

**问题：没有任何一个臂是在 qtx 的 408.5 token 预算上做聚类的。** 因此：

- 实验结果支持的是"**在 qtx 之下再压会掉分**"；
- 它**不支持**"聚类一旦遇到强选择器，增益就被吃掉" —— 后者是关于聚类**反事实贡献**的断言，需要 (a) 聚类单独使用时有正贡献、(b) 叠加后该贡献消失，两个条件。"压得更狠所以掉分"与"机制被吸收"是两件事，目前的臂结构分不开。
- 唯一能间接支持弱版吸收叙事的结果模式是 `qtx_cluster < qtx` 且 `≈ qtx_random`；实测 `qtx_cluster`(345.6 tok) 反而**优于** `qtx_random`(371.7 tok)，与该模式相反。

**修复**：加一个"在 qtx 同预算（408.5 tok）上重做选择"的臂，或把结论老老实实改成"再压 15% 掉 3.5 分"。

### 2.3 🟠 `--reduce-frac 0.25` 的实际削减幅度约为一半

`merge_reduce`/`random_reduce` 里 `merged += 2`，而每次合并只从输出移除 **1** 个 unit（两簇合一，代表元取最长成员）。故实际移除 ≈ `reduce_frac/2`：标称 25% → 实际 **~12.5%**。一切幅度陈述必须以输出表的 `ctx_tokens` 实测值为准（该表确实如实列了 token）。

## 3. GLM 提出、我判断成立的问题

### 3.1 隐私检查器（`v1_checker.py` / `v1b_diag.py`）

| 严重度 | 问题 |
|---|---|
| major | **`tokenset` 检查器在构造上被 `exposure_basic` 完全包含**（marker 作为 token 出现 ⇒ 必然连续 ⇒ 片段检查已命中）。它在 53,925 个 secret 上**零次独立触发**。"三层检查器"里的第三层是空的。 |
| major | **`account` 类型的 7 个变体全部被 basic 包含** —— account 的"变体探测"没有在测任何东西。去掉 marker 的改述（"his account id at the firm was cancelled"）对所有检查器隐形。 |
| major | **本工具产不出"按 email/phone/account 分类的 paraphrase 移除率"**：统计键退化成 `(tag,)`，`type` 从未写入任何桶。项目里分类型的数字只能来自 `paraphrase_probe`，不能引这个全量检查器。 |
| major | **`blind_spot = 0.00%` 是语料性质而非盲区不存在**：该语料只注入 canonical 形式，没有 paraphrase 群体。真实盲区（40% / 9.1%）只能引 `paraphrase_probe`。两个数字必须分开陈述。 |
| major | **修复后的 `redact_miss = 1.14%` 是检查器自身的假阳性地板，不是泄漏率**：它 100% 来自 phone 的 3–4 位数字块在已删净文本上的巧合命中（如 `"2020"` 含 `"202"`）。正则的真实漏删 ≈ 0%（`red_basic = 0.00%`）。不应引用为"正则前端泄漏 1.14%"。 |
| major | **`v1b_diag.py` 与 `v1_checker.py` 各自实现判定逻辑**（无共享 import，五块逻辑是逐行复制），且数字段规则**已经分叉**（诊断跑旧规则、checker 跑修正规则）。产出 1.14% 的那个谓词在诊断脚本里**从未被执行**，其约 615 个残留命中未被采样、未被归因。按本项目自己的教训（副本会漂移），1.14% 的可信度存疑。 |

### 3.2 PACT 迁移（`v3_batch.py`）

| 严重度 | 问题 |
|---|---|
| major | **用的是编码器最终层 `last_hidden_state`，不是 PACT 要求的早期层隐藏态**（L196）。attention-score-free 满足、真嵌入也满足，但"表示层"是机制的一部分，早期层与最终层产生的簇结构不同 → V3 全部结论的表示基础与宣称不符。 |
| major | **`rand4_emb` 结构上只能产生大小 = 2 的簇**（`pairs_random` 只做互斥相邻对），而 `bound_emb` 允许 size ≤ 4。所以 `bound_emb` vs `rand4_emb` 把**选择准则**和**簇大小**两个因素混在一起，无法支撑"是距离界而不是簇大小带来低混合率"这一归因。 |
| minor | `tau` 只约束**合并边**，链式合并可把相似度低于 tau 的成员装进同一簇（簇直径不受界约束）。若表述为"簇内相似度 ≥ tau"则言过其实。 |
| minor | `tau = 0.75` 写死在 L244，报告与 JSON **都不记录 tau / max_size / 编码器名** → 距离界实验的数字无法从产物审计。 |
| minor | 算法是**相似度贪心凝聚**，无密度 ρ、无 δ、无峰值选择。称"PACT 的 DBDPC 迁移"在方法部分会与代码对不上。 |

### 3.3 冻结数据（`build_crossdata.py`）

| 严重度 | 问题 |
|---|---|
| major | **email 的 paraphrase 变体是常量串** `"the contact email ending in invalid"`（域名固定 `example.invalid`），**不含任何 PII**（实测 distinct = 1/581，对照 phone 含尾 4 位、account 含完整 marker）。用它评估 email 型改述会**虚假通过**。同款坏模板也进了产出 9.1%/40% 动机数的 `paraphrase_probe`。 |

| minor | `simuhome` 实际只有 5 个任务文件（n=5），但 `note` 无条件写 `"ok"`。 |

## 4. 四象限路由器：**代码里不存在**

设计文档（`COMBINATION_SCHEMES.md` §3、`SCHEMES_V2.md`）把 2×2 路由器当作核心贡献，其中「**敏感且任务相关 → 泛化/原型替换**」是导师点名、也是声称最新颖、现在零覆盖的一格。

在全部 `.py` 里搜索 `quadrant|四象限|route|router|alias|category|类别|prototype|generaliz|泛化`：

- **零命中**（唯一命中是 `probe.py` 里一个 markdown 表头的中文"类别"二字）。
- 全部脱敏一律替换为 `[REDACTED]`，**没有任何原型注入 / 别名映射 / 类别标签替换的实现**。
- 「敏感 AND 任务相关」的判定分支不存在。

**结论：这一格目前只存在于文档里。** 它是文档中"最新颖"的部分，也是最需要落地的部分 —— 现有代码提供的隐私端只有"删除"一种操作。

## 8. 方法学教训（写给下一轮）

1. **"名义比例"不等于"实际预算"。** 只要指标是比率，就必须报告并核对**分母**。本次两条主结论都栽在这里。
2. **对照臂必须按实际达成的压缩量配准，而不是按请求的参数配准。** 参数是意图，达成量是事实。
3. **逻辑副本一定会漂移。** `v1b_diag` vs `v1_checker` 已经漂移过一次；复核脚本要用 `importlib` 导入被测代码本身。
4. **审计必须配对抗复核。** 本次挡掉了至少两条我自己提出的误报。
5. **文档声称 ≠ 代码实现。** 四象限路由器写在三份设计文档里，代码里一行都没有 —— 越是"最新颖"的部分，越要先搜代码再引用。
