## 22.2 三层加固

### 层一：脚本级守卫（硬拦截）

在 15 个会加载模型/做重计算的脚本顶部注入守卫，**无 `SLURM_JOB_ID` 即退出码 97**：

```python
# --- HPC_LOGIN_GUARD_V1 ---
import os as _os_guard, sys as _sys_guard
if not _os_guard.environ.get("SLURM_JOB_ID"):
    _sys_guard.stderr.write("\n[BLOCKED] 该脚本必须在 Slurm 作业内运行。\n"
                            "  正确做法: sbatch <你的.slurm>（优先 --partition=prod）\n\n")
    _sys_guard.exit(97)
```

覆盖范围：

- 本项目 `privtrim/` 下 **12 个**：`run_pc.py`、`gen_guiding.py`、`ext_compress2.py`、
  `run_intact.py`、`e2e_longctx{,_r2,_r3,_r4,_r5,_r5full,_r5full_ORIG}.py`、`ext_compress.py`
- 同账号 IVF 项目 **3 个**：`bench/dinov3_fewshot.py`、`work/lb_fusion_final.py`、
  `work/implant_pred.py`

安装脚本：`code/install_guard.py`、`code/install_guard_safe.py`
（后者带属主校验、符号链接拒绝、`.guard_bak/` 备份、插入后 `compile()` 自检）。

**本机验证（不连 HPC，纯逻辑测试）**：

| 条件 | 退出码 | 期望 |
|---|---:|---:|
| 无 `SLURM_JOB_ID` | 97 | 97 ✅ |
| `SLURM_JOB_ID=88888` | 0 | 0 ✅ |
| `SLURM_JOB_ID=''`（空串）| 97 | 97 ✅ |

### 层二：shell 级拦截（交互式）

`~/.hpc_login_guard.sh`（权限 600，仅本账号）+ `~/.bashrc` 一行 source。
拦截登录节点上的重命令，放行 `-m py_compile` / `-m pip` / `--version` 等轻量用法。

### 层三：执行规则（AI 侧约束）

6 份 `AGENTS.md`（工作区 ×5 + 用户级 `~/.dsh/AGENTS.md`），六条规则：

1. 登录节点禁止任何计算
2. 分区选择：能 CPU 就 `prod`，只有 CUDA-only 才 `gpu`
3. 提交规范：分片 + 每片单独落盘 + 「已存在则跳过」
4. 动作前自检：`ps ... | awk '$2>5'` 应只输出表头
5. 账号下所有脚本同等约束（已加固）
6. **验证优先在本机完成，减少 HPC 交互**

## 22.3 影响范围审计

所有改动**只落在本账号自己的路径**：

| 位置 | 内容 | 权限 |
|---|---|---|
| `~/.hpc_login_guard.sh` | shell 守卫 | 600 |
| `~/.bashrc` | 追加 1 行 source | 600 |
| `~/.../privtrim/*.py` | 12 个脚本守卫 | 本账号 |
| `~/.../hpc-ivf-sota-x20/` | 3 个脚本守卫 + `.guard_bak/` 备份 | 本账号 |

`/etc`、`/usr`、`/opt`、modulefiles 下**本账号拥有的文件数 = 0**。
其他账号登录时读取的是他们自己的 `.bashrc`，物理上无法受影响。

## 22.4 遗留与建议

- 原始文件备份：`bench/.guard_bak/`、`work/.guard_bak/`
- 若需运行：写成 slurm 脚本提交；直接 `python xxx.py` 会被拒绝（退出码 97）

## 22.5 教训

1. **"省时间"不是理由**：`prod` 分区当时完全空闲，提交作业比我图省事地跑登录节点更快
2. **验证也要验证**：我先后三次因测试脚本自身的缺陷（`$?` 被子命令重置、相对路径未 `cd`、
   `bash -ic` 横幅淹没输出）误判守卫失效，差点得出相反结论
3. **本机能测的不要上集群**：守卫逻辑是纯 Python，本机 3 项测试即可覆盖，
   完全不需要连 HPC
