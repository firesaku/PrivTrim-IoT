## 1. 为什么是 Mistral-7B-Instruct-v0.3

审稿人最直接的一刀是"你的结论是不是 Qwen 特有的"。要堵这个口，第二个模型必须
**换家族、不换量级** —— 如果同时换家族和换尺寸，增益变化就分不清是家族差异还是
规模差异。Mistral-7B 与 Qwen2.5-7B 同为 7B 级、同为 chat 模型，是干净的对
照；它还是**不 gated**（不需要人工批许可证），当天就能拿。

顺带说明为什么不用 Qwen2-0.5B（集群里唯一另一个本地模型）：0.5B 在这种
18k token 的多跳检索上很可能全臂贴地，差异会淹在噪声里，**换不来一个可信的对照**。

## 2. 提交前的五项检查（全部离线完成，没占 GPU）

| # | 检查项 | 方法 | 结果 |
|---|---|---|---|
| 1 | 模型下载完整性 | `snapshot_download` 返回 DONE + 目录比对 | ✓ 29 GB，13 文件 |
| 2 | chat template 可用 | `tokenizer.chat_template` 非空 + 实渲染一次 | ✓ YES，渲染 15 token |
| 3 | **上下文会不会超 maxlen** | 用 Mistral 分词器实测 112 案例 | ✓ 最长 **19838** < 24576，超限 **0/112** |
| 4 | **`pad_token=None` 会不会炸批生成** | 读 r4 源码第 484–486 行 | ✓ 已兜底：`pad_token=eos` + `padding_side='left'` |
| 5 | 有没有 Qwen 专属硬编码 | grep `im_end`/`qwen`/`<\|` | ✓ 只有注释与 help 文本，`--lm` 是唯一模型入口 |

第 3 项是必须做的：Mistral 的分词器与 Qwen 不同，同一个文本的 token 数会变。
Qwen 下最长 18608，Mistral 下 19838（多 6.6%，因为词表切分不同）。24576 仍有余量，
所以 `--maxlen-policy raise` 不会触发 —— 一旦触发就会中止整个作业，属于"必须提前
验掉"的风险。

第 4 项是最可能静默踩的坑：Mistral 的 tokenizer 本身没有 pad token，批生成要
左 padding。本项目早期就栽在 padding 上，这次先读源码确认已兜底才提交。

## 3. 一个被证伪的"预检通过"

我本想用 `--dry-run` 预检 0.10 / 0.15 这种极端预算会不会突破预算上限
（`drop_to_budget` 在锚点内容本身就超过 B 时会 raise，那会毁掉整批结果）。
dry-run 跑完、没报错、还打出了 0.10 的完整表格 —— 看起来是"通过"。

**但它不是。** dry-run 的表头写着：

> `*** DRY-RUN：未加载模型、token 数为 词数×1.33 估计`

也就是说 dry-run **根本不调 tokenizer**，用的是 `词数×1.33` 的字面估计，而实测
真实 token 数约是这个估计的 2.8 倍。于是：

- dry-run 里 `B = 0.10 × 估计值` 比真实 B **更小**；
- 但整个预算对账、`drop_to_budget`、锚点保护都是在**估计数**上算的；
- 所以"没 raise"只证明**代码路径能跑通**，不证明**真实预算能对上**。

结论：极端预算（0.10/0.15）目前**没有有效预检**。要验必须在集群上用真 tokenizer
跑一遍 `build_arm_texts`（不需 GPU），或者接受"可能 raise 掉整个作业"的风险。
这两条都没做，所以这一档先不提交 —— 先把主要缺口（第二个模型、外部基线）补完。

**教训**：dry-run 通过 ≠ 真实运行会通过。看预检结果前先确认它到底走了哪条代码路径。
