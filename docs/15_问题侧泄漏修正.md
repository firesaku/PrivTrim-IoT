# 15 · 修正：「零泄漏」是上下文口径，问题一侧一直在泄漏

> 2026-10-17 ｜ 发现方式：对抗式复查（`patch_alias_question.py` 复查的 C1）
> 性质：**对我上一轮结论的修正**。`docs/14` 里"值泄漏 0.00%，判据通过"这句话必须加限定。

---

## 1. 问题

`leak_of(case, text)` 只对**上下文**跑 `privcheck.exposure_basic`，从不看问题字符串。
但模型真正读到的是 `make_prompt(问题, 上下文)` —— **提示词 = 问题 + 上下文**。

于是所有"上下文已脱敏"的臂都报 `leakV = 0.00%`，而它们的问题里原样写着被查询的实体：

```
In the log above, which persona id is recorded for the account ACCT-5ee052b431dc?
```

`ACCT-5ee052b431dc` 是 `canary`，`case['target_entity']` 就是它。**这正是四象限里
"敏感且相关"那一格** —— 也就是整篇论文的核心那一格。

## 2. 实测（模型无关，离线算；112 个案例）

| 臂 | 关 `--alias-question` | 开 `--alias-question` |
|---|---:|---:|
| `alias` / `alias_budget` ×3 / `alias_budget_link` ×3（共 7 格） | **40/112** | **0/112** |
| `delete` / `delete_budget` ×3 | 40/112 | 40/112（不在 `ARMS_ALIAS` 里） |
| `budget_cluster` / `budget_cluster_link` / `budget_random` | 40/112 | 40/112 |
| `full` | 40/112 | 40/112 |

**21 个臂格里，关 flag 时全部 40/112 问题侧泄漏** —— 这是问题格式的属性，不是某个臂的毛病。
开 flag 后只有 7 个别名臂格降到 0。

### 对已发布数字的具体影响

| 上一轮的说法 | 修正后 |
|---|---|
| `alias_budget_link` 值泄漏 0.00%，判据通过 | **上下文口径** 0.00%；**提示词口径** 40/112 泄漏被查询实体。加上 `--alias-question` 后才真正为 0 |
| `delete` / `delete_budget` 值泄漏 0.00%（r3 就报过） | 同样只是上下文口径。它们的提示词里那 40 个案例仍带着实体原值 |
| `budget_cluster_link` 泄漏 6.03% | 该数字是上下文口径；提示词口径还要**并上**那 40 个问题侧案例 |

## 3. 为什么这不是坏消息

这个修正反而让四象限的结论更硬：

| 配置 | 提示词层被查询实体是否泄漏 | 任务 F1（multi_entity） |
|---|---|---|
| `full`（不处理） | 泄漏（问题 + 上下文都带） | 0.6083 |
| `budget_cluster`（只压缩） | 泄漏（问题带） | **0.0000** |
| `delete` / `delete_budget`（删） | **泄漏（问题带）** | **0.0000** |
| `budget_cluster_link`（保锚点，不脱敏） | 泄漏（问题 + 上下文都带） | 0.5500 |
| **`alias_budget_link` + `--alias-question`** | **不泄漏（0/112）** | 待测（作业 10602439） |

也就是说：**在"敏感且相关"这一格上，只有"问题与上下文同步别名化"能同时做到
"不泄漏被查询实体"和"任务还有救"**。删除式脱敏看起来零泄漏（上下文口径），
实际上既泄漏（问题口径）又毁任务。这正是四象限要讲的那件事，而且现在有数字。

## 4. 待办

1. **把问题侧泄漏并进主表**：`leak_of` 加一问 `q`，产出
   `(ctx_v, ctx_f, q_v, q_f, n)`，主表加 `q_leak` 列。
   否则"零泄漏"在产物里**不可验证**。
2. **`ARMS_ALIAS` 的名单与注释矛盾**：注释说"会改写实体表面串的臂"，
   但 `delete`/`delete_budget` 同样改写（改成 `[REDACTED]`）却不在名单里 →
   它们的问题侧泄漏永远不会被任何断言看见。要么扩名单，要么改成显式语义声明。
3. **外部臂绕过问题改写**：`ext_mask_llmlingua2` 是脱敏方法，上下文脱敏了、问题没脱敏，
   与我们的别名臂对比时**不对称**（差异里混进了"我们给自己打了补丁"）。
   对比表里必须标注，或给 ext 臂也加上问题改写。
4. `docs/14` 的结论段要按本文修正。

## 5. 顺带：一个免费的内置难度对照

`alias` 是 `ratio=None` 的**长度保持臂**（不压缩，只把上下文实体换别名）。
开 `--alias-question` 后：

- 若它回到 ≈ **0.7189**（= `full` 的真跑值）→ 别名**表示**本身不改变任务难度，
  于是 multi_entity 从 0.0250 的回升可以干净地归因到"问题不再断链"；
- 若明显低于 0.7189 → 别名表示**本身**就在损害任务（例如 `[ACCOUNT-A]` 与
  `[ACCOUNT-F]` 只差一个字母，判别粒度比 12 位 hex 更细），那么外推要打折。

**它同时是断链诊断的独立检验**：如果诊断正确，长度保持 + 问题别名化就应该恢复到
接近 `full`；恢复不了就说明还有第二个机制在起作用。作业 10602439 的产物直接给答案。
