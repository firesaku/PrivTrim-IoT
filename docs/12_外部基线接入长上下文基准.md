# 12 · 外部基线接入长上下文基准（设计与跑前检查）

> 2026-10-17 ｜ 目的：回答"冗余度压缩在多实体案例上系统性失效，是领域问题还是我们自己实现的产物"
> 原则：只用已发布方法的**输出文本**，不重实现、不改其代码；跑前先做独立复查

---

## 1. 为什么必须做这件事

在此之前，所有数字都是我们自己内部臂互比：`budget_cluster` vs `budget_random` vs
`budget_cluster_link`。这能证明"锚点保护有用"，但**完全不能证明**"已发布的冗余度
压缩方法在这个场景上会失效" —— 后者才是能撑起一篇论文的那个论断。

审稿人的第一刀必然是：你挑的 `budget_cluster` 是不是你自己实现得太差？

唯一能回答的办法：把已发布的方法放到**同一个基准、同一个模型、同一条生成+打分+泄漏
诊断路径**上跑。

---

## 2. 一个关键发现：压缩器根本没在 HPC 上跑过

`common.py` 的 `model_path()` 直接返回 manifest 里的路径，而 manifest 里是：

```
D:\Shijie Zeng\CodeX\cybersec_IoT\models\models--google--flan-t5-small\snapshots\0fc9ddf...
```

Windows 路径。而集群上 `.venv-main` 里连 `llmlingua` 都没有。也就是说
**batch1 的压缩阶段是在本机 Windows（RTX A6000）上跑的，HPC 只做 LM 评测**。

核实结果：本机 `D:\Shijie Zeng\CodeX\cybersec_IoT\` 下代码、6 个模型、
`.venv-compression-batch1`（torch 2.6+cu124，CUDA True）全部齐备。

**结论：外部基线整条可以在本机跑**，不占 HPC 卡。这比原计划的"先写 schema
adapter 再上 HPC"省得多。

## 3. 适配器只做 schema 翻译

`ext_compress.py` 的设计约束：**不重实现任何算法**。

```python
sys.path.insert(0, batch1_dir)
import common as C      # 已发布原码
import compress as K    # 已发布原码
run, cache, stats, info = K.load_method(method, tok)
r = K.compress_case(adapted_case, method, run, cache, stats, tok)
```

唯一的改动是字段名：

| 长上下文案例 | batch1 期望 | 说明 |
|---|---|---|
| `key` | `id` | 字段名差异 |
| `question` | `question` | 相同 |
| `context` | `context` | 相同 |
| （无） | `original_tokens` | 现场用 tokenizer 实测补上 |

### 预算口径（必须说清）

`compress.py` 里 `budget = n // 2` 是**写死的 0.5**（`floor(0.5*n)`）。
本项目用 `round(0.5*n)`。两者在偶数上完全相同，奇数上最多差 1 token。

所以：**不动任何已发布代码就能拿到精确的 0.5 档对标** —— 而 0.5 正是我们主结果
所在的那一档。这也是"不解锁其他 ratio"的理由：0.25/0.75 需要改动已发布代码，
那就不是原码了。

## 4. 冒烟结果与一个必须记录的能力边界

短案例（2.2k token）× 7 方法：全部 `status=ok`，`matched.tokens == target`。

耗时（2 例合计）：`full` 0.1s、`mask_llmlingua2` 2.3s、`quito_x` 8.7s、
`provence` 26.8s、`cpc` 66.6s、`dac` 124.4s。

**但真正的风险在长案例。** 三个方法内部有 512 的窗口限制，各自报警：

| 方法 | 告警 | 含义 |
|---|---|---|
| `quito_x` (flan-t5-small) | `19670 > 512` | T5 分词器声明上限 512 |
| `provence` (debertav3) | "contexts were split into several pieces ... limited context length of Provence which is equal to 512" | 作者自己 warn：**切成 512 块再剪** |
| `llmlingua2` (xlm-R) | `2628 > 512` | xlm-R 上限 512 |

`provence` 那条是作者**明确写出来的**行为：它把长上下文切成若干 512 片段分别剪枝，
**剪枝决策没有全局视野**。

### 这条为什么危险

如果不查，最坏情况是这样：某个方法把 18k token 的上下文只按前 512 token 做决策，
**其余原样返回**；预算对账上 `matched.tokens` 仍然被 `prefix_budget` 裁到 = target，
表格里一切正常 —— 于是我会把"它只看了前 2.8% 的上下文"误报成"它被公平地打败了"。

**必须区分这两种情况。** 计划中的检查（model-free，不改基线代码）：

> **位置覆盖率**：把原上下文按位置切成 10 等份（decile），把输出里的每个句子用
> 词面匹配回溯到它来自哪个 decile，统计输出 token 在各 decile 上的分布。
> - 真正全局剪枝的方法：token 应散布在 10 个 decile 上；
> - 只看前 512 token 的方法：token 会**全部集中在 decile 1**。
>
> 这个检查同时是一个**独立发现**：可以量化"512 窗口的压缩器在 18k 上下文上
> 实际只覆盖了 x% 的位置"。

在跑出这张分布之前，任何"基线在多实体案例上失效"的说法都**不能写进论文**。

## 5. 打分路径的接入方式：注入文本，不接它们的评估代码

给 `e2e_longctx_r4.py` 加 `--ext-arms <jsonl>`，把外部方法产出的上下文**原样注入**
与内部臂逐字相同的生成 + 打分 + 泄漏 + 实体诊断路径。

- 只用输出文本，任何中间量都不用 → 唯一变量是"这段上下文怎么来的"；
- `arm_style('ext_*')` 自然落到 `'none'` 分支（不含删除/别名语义），语义正确；
- 两处按 `ARMS_BUDGET` 的作用域过滤已改为同时接受 `ext_*`，否则它们会掉进
  "长度保持块"，那是语义错误。

### 跑前检查（已做）

| 检查 | 结果 |
|---|---|
| `py_compile` | 通过 |
| 补丁前后 dry-run（不带 `--ext-arms`），三产物 SHA256 | **完全相同**（28220 / 45531 / 1020219 字节） |
| 独立子代理对抗式复查 | 进行中（10 项怀疑清单：记账一致性、作用域、静默丢臂、`matched` vs `native` 的公平性、tokenizer 一致性、`entity_diag` 对塌缩的可见性、512 掩盖问题） |

**一次假通过要记下来**：第一次 dry-run 对比时，两次运行都因控制台 cp1252 编码
`UnicodeEncodeError` 崩掉、产物 0 字节，而我的哈希比较把"两个不存在的文件"
判成了 `IDENTICAL`。是"先看预检走了哪条路径"这条教训的第二次实例 ——
**比较前必须先断言文件存在**。

## 6. 算力安排

`dac` 在 2.2k token 上是 62s/例。112 例 × 18k token 若线性外推是十几小时。
`compress_case` 每例自己 `cache.clear()`，**案例之间无状态**，所以按案例分片
（多进程，各自 load 一份方法）是安全的，且不改动已发布代码的任何逻辑。

本机 A6000 48GB，这些方法最大的模型是 1B，分片并行空间充足。
