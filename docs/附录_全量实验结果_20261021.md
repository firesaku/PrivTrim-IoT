## 4. DAC 的失败模式（重要，写入 limitation）

DAC 在 396 例对照集上：

| 状态 | 案例数 | 平均 token | 最大 token |
|---|---:|---:|---:|
| `ok` | 300 | 4,827 | **8,790** |
| `error` | **96** | **16,663** | 18,608 |

失败原因（原样）：

```
19.09 GiB is reserved by PyTorch but unallocated.
CUDA out of memory.  (original_tokens=18242)
```

**DAC 在 141 GB 的 H200 上无法处理约 9k token 以上的上下文**，
96 个失败案例的平均长度是成功案例的 3.5 倍。

因此 DAC 的 0.1113 是**在较短的 300 例上**测得的，与其余臂的 2,728 例不可比。
正确表述：**"DAC 无法在本基准的长上下文上运行（96/396 例 CUDA OOM），
不具备可比性"**，而不是"DAC 效果差"。

它的成本也支持这一结论：单例 35.9 s（p95 81.8 s），全量 2,328 例需 27 GPU-小时，
是其余五个方法合计（3.4 GPU-小时）的 8 倍。

## 5. 方法学注意（写论文必须交代）

1. **本 pipeline 是确定性的**：`do_sample=False` 纯贪婪；`--seed` 参数在代码里
   **声明但从未使用**（无 `manual_seed` / `np.random` / `random.seed`）。
   因此**多种子会产出逐字节相同的结果**，不能用它估计方差。
   本文方差来自**跨案例配对 bootstrap**。
2. **跨运行并非逐位可复现**：同一个 `full` 臂两次独立运行 F1 = 0.6079 vs 0.6085
   （≈1–2 个案例），指向 fp16 算子非确定性。
   **任何小于 ~0.001 的 F1 差异都不应解释为方法差异。**
3. **batch=8 更慢且非严格批不变**：分片 0 上 18:02 vs batch 2 的 14:28（慢 25%），
   1,806 次生成中 4 次输出不同（99.779% 一致）。原因：上下文长度 2k–24k 差异极大，
   左 padding 到 batch 内最长序列，批次越大浪费越多。
4. **管线交叉校验**：`ext_full` = 0.6078、`full(max32)` = 0.6079、内部 `full` = 0.6078，
   三次独立测量在四位小数一致。
5. **DAC 的 96/396 OOM 是架构性的**，不是超时或调参问题。

## 7. 新增对照：INTACT（文本匿名化，非同模态压缩）

> 来源：`IldikoPilan/text_sanitization`（INTACT, INference-guided Truthful sAnitization）
> 跑法：Mistral-7B-Instruct-**v0.3** fp16（仓库默认 v0.2、4-bit；因本环境 accelerate 版本
> 与仓库钉死的 0.26.1 不兼容，4-bit 会抛 `.to is not supported for 4-bit bitsandbytes models`）
> 实体映射：`account -> CODE`（规则）、`email/phone -> MISC`（LLM）——TAB 体系无 EMAIL/PHONE
> 候选选择：取 `replacements_[0]`，**未跑 `guess.py`** 的推断式挑选

### 7.1 规模与泄漏（100 例，1,506 个 canary）

| 项 | 数值 |
|---|---|
| 文档 | 100 |
| 实体 | 1,506（全部生成替代值）|
| canary 残留 | 1,506 → **7**（99.5% 消除）|
| token 保留 | 215,076 → 205,017（**95.32%**）|

### 7.2 QA 效用（同一批 100 例）

| 臂 | F1 | EM | 目标实体留存 | 泄漏 | 平均上下文 token |
|---|---:|---:|---:|---:|---:|
| **INTACT** | **0.0000** | 0.0000 | **0.000** | 4% | 2,050（95%）|
| 原始全上下文 | 0.6900 | 0.6900 | 1.000 | 100% | 2,151 |
| **OURS@0.50** | **0.9200** | 0.9200 | 1.000 | **0%** | 1,043（48%）|
| **OURS@0.20** | **0.8300** | 0.8300 | 1.000 | **0%** | 416（19%）|

配对检验：`INTACT − OURS@0.50 = −0.9200`，CI `[−0.9700, −0.8700]`，**0 胜 92 负**。

### 7.3 为什么 INTACT 的 F1 归零（关键解释，不是实现缺陷）

这批案例的问题**直接点名敏感标识符**：

```
question     : which persona id is recorded for the account ACCT-fc668719b347?
target_entity: ACCT-fc668719b347      ← 同时是一个 canary
```

INTACT 把该账号替换为 `CODE_0`，上下文里不再有它，但**问题仍按原标识符提问**，
模型只能回答 UNKNOWN → 全量 EM/F1 = 0。

这就是设计文档里说的 **referential dangling trap**：脱敏脱离了与提问的同步。
`OURS` 之所以不掉，是因为所有臂都带 `--alias-question`（问题同步别名）——
这与主实验 `link vs 非 link` 的 +0.3009 是同一机制的两个侧面。

**正确的表述**：INTACT 在"问题引用敏感标识符"的任务上不可用，而非"INTACT 效果差"。
在问题不点名标识符的任务上其效用不会崩塌，本基准未覆盖那种设置。

### 7.4 必须写进 limitation 的五点

1. 仅 100 例子集（前 100 例，全为 `pec_home / multi_entity`），不代表 2,728 例全体
2. 未跑 `guess.py`，取第一个候选而非推断式挑选
3. Mistral **v0.3** 而非仓库默认 v0.2；**fp16** 而非 4-bit
4. `email/phone → MISC` 的实体映射是为绕开 TAB 实体体系的限制，属近似
5. 该对比锚定在"等隐私"（双方泄漏≈0），**不是**等预算；INTACT 长度只降 4.7%

### 7.5 Zeal 不能进这张表

Zeal（IEEE IoT-J 2025）作用在 **64 位 IEEE-754 浮点数**上，无 token/实体概念，
无法产出上下文文本。其本地验证套件已复现（`zeal-deck/validation_report.json`）：
密度归一化 1.000、Theorem 1 残差 0.0177、LDP 上界 `sup = e^ε`、`Ā=Thm7` 时可达性
7–30% → **100%**。定位应为「前作/动机」，不是基线。

## 8. 三项补充实验（①秩泄漏 → ②INTACT 同步 → ③跨模型）

### 8.1 ① 别名秩泄漏：真实存在，且修复免费

`v4_router.Aliaser` 在未设 `PT_ALIAS_KEY` 时按 `(type, value)` **升序**发别名。
攻击者若知道该文档的值集合（如来自库泄露），按升序配对即全逆推。
**主实验全程未设该 key**，因此原报告的 `leak = 0` 是在带秩泄漏的分配下测得的。

| 防守设置 | 攻击命中率（300 例 / 4,512 个别名）|
|---|---:|
| 未设 `PT_ALIAS_KEY` | **100.0%**（4512/4512）|
| 设 `PT_ALIAS_KEY` | **19.1%**（864/4512）—— k=5 的随机猜中率即 20% |

修复对效用的代价（同 300 例，唯一变量是环境变量）：

| 臂 | F1 无 key | F1 有 key | Δ |
|---|---:|---:|---:|
| full | 0.7200 | 0.7200 | +0.0000 |
| alias | 0.5800 | 0.5500 | −0.0300 |
| **alias_budget_link@0.5** | **0.9333** | **0.9333** | **+0.0000** |

**结论：主臂完全不受影响，修复免费。论文应默认启用 `PT_ALIAS_KEY`。**

### 8.2 ② INTACT 加上问题同步后 F1 完全恢复

8.1 之前的 100 例对比中 INTACT 的 F1 = 0，是因为它的脱敏没有同步到 question。
把 INTACT 的 `span_text → replacement` 映射同样应用到 question 后：

| 臂 | F1（未同步）| F1（已同步）| Δ |
|---|---:|---:|---:|
| **ext_intact** | **0.0000** | **0.7300** | **+0.7300** |
| ext_full / full | 0.6900 | 0.0000 | −0.6900 |

（`ext_full`/`full` 在同步设置下掉 0 是预期的：question 问 `CODE_5`，而原始上下文里只有 `ACCT-...`。）

**这修正了此前的表述**：不能说"INTACT 在长上下文任务上不可用"，应该说
**"INTACT 在问题引用敏感标识符且未做同步时不可用；补上同步后 F1 = 0.7300"**。

修正后的等隐私对比（同一批 100 例）：

| 方法 | F1 | 泄漏 | 上下文 token 保留 |
|---|---:|---:|---:|
| INTACT（已同步）| 0.7300 | ≈0 | **95%** |
| **OURS@0.20** | **0.8300** | 0% | **19%** |
| OURS@0.50 | 0.9200 | 0% | 48% |

**我们在两个轴上同时更好**：同等隐私下 F1 更高，且长度只要它的 1/5。

### 8.3 ③ 跨模型泛化：机制成立，但"压缩优于全上下文"不成立

Mistral-7B-Instruct-v0.3 vs Qwen2.5-7B，同 300 例、同预算 0.5：

## 12. 2025/2026 外部基线的可行性核查（逐条带证据）

目标要求"加入 2025/2026 外部基线"。核查了 5 个候选，**没有一个能在当前条件下按作者配置跑通**，
每条都记录了具体阻塞点，而不是笼统的"找不到"。

| 候选 | 出处 | 核查结果 |
|---|---|---|
| **AttnComp** | AAAI 2025 | GitHub 搜到的 `ZZR0/AttnCompress` **是另一篇论文**（Dynamic Attention-Guided Trajectory Compression for *Software Engineering Agents*，AgentDiet/Trae），需 ~$2k LLM 费用 + 2 个月 + 500GB，任务域也不同 → **不适合作基线** |

- `KiSCompressor` / `SCRLCompressor` — 见上表，不可用

其余依赖（`sentence-transformers`、`tiktoken`、`icecream`、`pynvml` 等）都可安装。
guiding questions 需按作者格式生成一份（可用现有模型自动生成），这是唯一的额外工作量。

### 12.3 建议的表述

> 我们覆盖了 8 个已发表压缩基线与 1 个脱敏基线（INTACT）。

## 13. 对第 11.3 节的更正：Type B 实验与 link 失效的真实原因

### 13.1 更正内容

第 11.3 节原写："**`link` 机制贡献为 0，因为 LongBench 的问题不引用注入的 canary**"。
这个解释**不完整**，经 Type B 实验证伪。

### 13.2 Type B 实验（公开上下文 + 引用 PII 的合成问题）

构造：复用 300 例公开上下文的 device-log 块，解析出 `{"device":X,"account":Y}`，
问题改为 `Which device is associated with account Y?`，gold = X，
并补上 `target_entity = Y`（否则 link 机制完全不会被触发——这是第一次跑错的原因）。

| 臂 | F1（A 原问题）| F1（B 引用 PII）| Δ |
|---|---:|---:|---:|
| full | 0.4181 | **0.9864** | +0.5683 |
| alias | 0.4074 | 0.9231 | +0.5156 |
| **alias_budget_link** | 0.4167 | **0.3100** | −0.1067 |
| alias_budget | 0.4167 | 0.3100 | −0.1067 |
| ext_cpc | 0.4515 | 0.0474 | −0.4041 |
| ext_llmlingua2 | 0.3710 | 0.1100 | −0.2610 |

**两臂仍然完全相同**（`ctx_tokens` 在 300 例上逐例相等，`dF1` 精确 0.0000）。

### 13.3 真实原因（代码级）

`alias_budget_link` 与 `alias_budget` 的唯一差别是排序函数：

```python
order_a  = order_fn(ali_units, ans_of(ali_units))
order_al = order_fn(ali_units, [a or p for a, p in
                    zip(ans_of(ali_units), protect_of(ali_units, ali_keys))])
```

而 `protect_of` 的用途（代码注释原文）是：
> 除**答案承载单元**外还要保护"链接锚点"单元

Type B 里 device 与 account **在同一行记录中**：

```json
{"device": "sensor_4cd0_02", "account": "ACCT-4cd02ed8fb3a", ...}
```

锚点单元因"含答案"已被 `ans_of` 保留，`protect_of` 无增量
→ `order_al ≡ order_a` → 两臂必然同值。

**所以正确表述是**：`link` 只在「链接锚点单元 ≠ 答案承载单元」时才有作用。
Type B 的构造不满足这个前提，因此它**不能用来检验 link**。

### 13.4 这对第 11 节结论的影响

- **第 11.2 表的数字仍然有效**：公开基准上（原问题）我们 0.4167、与全上下文统计等价、
  显著低于 CPC。这是对**「别名 + 预算压缩」这一组件**的外部效度检验，结论成立。
- **但第 11 节不能声称"link 在公开数据上失效"**：没有做过有效检验。
- 要真正检验 link 的跨数据集泛化，需要构造「锚点与答案分属不同单元」的公开任务，
  例如把记录拆成两行：`account: Y` 与 `device: X` 分属不同 unit。

### 13.5 二次修正说明

本轮共修正自己两处错误：
1. 第一版 Type B 未设 `target_entity` → link 路径完全未触发
2. 补上 `target_entity` 后仍为 0，才发现是**同单元冗余**问题，而非"问题未引用 canary"

## 14. Type C：link 机制在公开上下文上的有效检验（结论：生效）

### 14.1 为什么前两个版本检验不了

| 版本 | 构造 | 为何无效 |
|---|---|---|
| Type A | LongBench 原问题 + 注入 PII | 问题不引用 PII，link 无事可做 |
| Type B | 问题引用账号，但 device 与 account **同一行** | 锚点单元已含答案，`protect_of` 无增量 → 两臂必然同值（300/300 `ctx_tokens` 相等）|
| **Type C** | **两跳：`account ACCT-X belongs to user U-Y`（一行）/ `user U-Y operates device sensor-Z`（另一行）** | 锚点单元与答案单元分离，`protect_of` 才有增量 |

Type C 自检：gold 在上下文中 300/300；锚点单元与答案单元分离 300/300。
另外修正了初版构造缺陷——设备名原本内嵌账号哈希（`ACCT-da10` → `sensor_da10_04`），
模型可纯字符串推断，已改为与账号无关的随机串。

### 14.2 结果（300 例，Qwen2.5-7B，预算 0.5，PT_ALIAS_KEY 启用）

| 臂 | F1 | EM | 目标实体留存 | ctx_tokens | 泄漏 |
|---|---:|---:|---:|---:|---:|
| full（全上下文）| 0.0967 | 0.0833 | 1.000 | 8,871 | 100% |
| alias（仅别名）| **0.7044** | 0.6833 | 1.000 | 8,860 | 0% |
| alias_budget（压缩，无 link）| 0.0733 | 0.0733 | 1.000 | 4,404 | 0% |
| **alias_budget_link（压缩 + link）** | **0.2000** | 0.1933 | 1.000 | 4,402 | 0% |

配对检验：

```
link − nolink   +0.1267  [+0.0789,+0.1756]  win 50 lose 11   ✓ 显著
abl − full      +0.1033  [+0.0500,+0.1567]  win 54 lose 21   ✓
alias − full    +0.6078  [+0.5522,+0.6667]  win 192 lose 4   ✓
ab − alias      −0.6311  [−0.6856,−0.5711]  win 8 lose 198   ✓
```

### 14.3 结论

**`link` 机制在公开上下文上成立，但前提是「锚点单元 ≠ 答案承载单元」。**
这解释了此前所有观察：

- 自建集（多实体，账号记录与属性记录分离）→ link 增益 +0.33
- LongBench 原问题 → link 无事可做（0.0000）
- Type B（同行记录）→ 锚点与答案同单元 → 0.0000
- **Type C（两跳分离）→ link 增益 +0.1267，显著**

因此论文可以写：
> link 的收益依赖于任务中存在「引用锚点」与「答案承载」分离的结构；
> 在具备该结构的任务上（自建多实体集、LongBench 两跳变体）均观察到显著正增益。

### 14.4 一个需要解释的异常

Type C 上 `full` 只有 0.0967，而 `alias`（不压缩、仅别名）高达 0.7044。
即**仅做别名替换就能让两跳任务从几乎不可答变为可答**。

推测：原始上下文里 5 个账号都是 12 位十六进制串，模型难以在长文中跟踪；
替换为 `[ACCOUNT-A]`…`[ACCOUNT-E]` 后显著缩短且可区分，相当于降低了检索难度。
**这说明该合成任务的绝对数值不宜直接引用**，但**配对比较（link vs nolink）仍然有效**，
因为两臂的别名处理完全相同、唯一差别是单元选择顺序。

Type C 的定位应是**机制检验**，不是主结果。
