### 3.5 提问方式稳健性（机械改写，不调用模型）

基准的问题是**模板化**的，所以必须检验"结论是否只在这一种问法下成立"。
用纯正则把问题改写成两个自然变体（实体值与属性名逐字保留、gold 不变，
自检确保 gold 不因改写泄入问题）：

```
原版: In the log above, which persona id is recorded for the account ACCT-X?
变体A: For the account ACCT-X in the log above, what is the recorded persona id?
变体B: Which persona id is associated with the account ACCT-X in the log above?
```

**判据是臂间差，不是绝对 F1**（问题文本不同，绝对值不可比）。两个变体各跑一个独立作业
（变体 A = 10602547，变体 B = 10602560，均为 9 臂 × 3 预算、112 例、21 prompt/例），
因为改写改变了 prompt 序列，不能沿用原批量结果。各臂 token 数在两变体中**逐位相同**
（`full` 7964、`budget_cluster_link` 3706、`alias_budget_link` 3708），
说明改写只动了问句、预算匹配没有变。

臂级 F1（同一臂跨问法对比才有意义）：

| 臂 | 原问题 | 变体 A | 变体 B |
|---|---|---|---|
| `full`（不压缩） | 0.7189 | 0.6831 | **0.6575** |
| `budget_cluster_link@0.5`（我们） | 0.7182 | **0.7441** | 0.7170 |
| `alias_budget_link@0.5`（我们） | **0.7450** | 0.7262 | 0.7170 |
| `budget_cluster@0.5`（纯冗余度） | 0.4688 | 0.5402 | 0.4420 |
| `alias_budget@0.5` | 0.5134 | 0.5848 | 0.4598 |
| `alias`（长度不变，只换标识） | 0.6719 | 0.6618 | 0.6385 |
| `delete` | 0.4916 | 0.4739 | 0.4705 |

判据与成对 bootstrap（Δ = 改写 − 原；**"是否保持"只能由 bootstrap 判，不能看绝对值**）：

| 判据 | 原 | A | A 的 Δ [95% CI] | B | B 的 Δ [95% CI] |
|---|---|---|---|---|---|
| **锚点增益（原始串）** | +0.2495 | +0.2039 | −0.0456 [−0.1170, +0.0258] 含 0 | **+0.2750** | +0.0255 [−0.0191, +0.0778] 含 0 |
| 锚点增益（别名） | +0.2316 | +0.1414 | **−0.0902 [−0.1696, −0.0188] 不含 0** | **+0.2571** | +0.0255 [−0.0115, +0.0676] 含 0 |
| `link` 相对不压缩 | −0.0006 | +0.0610 | +0.0617 [−0.0107, +0.1344] 含 0 | +0.0594 | +0.0601 [−0.0054, +0.1280] 含 0 |
| `alias_link` 相对不压缩 | +0.0261 | +0.0432 | +0.0170 [−0.0611, +0.0934] 含 0 | +0.0594 | +0.0333 [−0.0283, +0.1007] 含 0 |

**怎么读这张表（三句话）**：

1. **核心对比在三种问法下都成立**：锚点保护 − 纯冗余度 = **+0.20 / +0.25 / +0.28**，
   两个变体的 bootstrap Δ 都含 0（改写没有显著改变这个差值）。这正是"领域级问题、
   不是自实现问题"所需要的稳健性。
2. **别名那部分增益方向一致、大小随问法浮动**：+0.14（A）/ +0.23（原）/ +0.26（B）。
   只看变体 A 会得出"对问法敏感、缩小 39%"；只看变体 B 会得出"完全稳健"——**两个
   变体的 bootstrap 结论正好相反（A 不含 0、B 含 0），所以两者都不能单独引用**。
   正确写法：**别名增益在 0.14–0.26 之间随问法浮动，但始终为正、量级大；不能说它稳定，
   也不能说它会被问法消掉。** 这条不确定性的来源是问法而不是我们的实现。
3. **换问法首先伤的是不压缩上下文**：`full` 从 0.7189 掉到 0.6831 / 0.6575
   （−0.0358 / −0.0614），两个锚点保护臂几乎不动（0.718→0.744→0.717、0.745→0.726→0.717）。
   于是"我们 vs 不压缩"的符号在改写后翻正（−0.0006 → +0.059），**不是我们变强，
   是基线更怕换问法**；这句话必须按这个方向写，不能写成"超过无损上下文"。

一个必须自己说破的细节：变体 B 里 `alias_budget_link@0.5` 与 `budget_cluster_link@0.5`
**同为 0.7170（六位小数相同）**，但案例级并不相同（**6 例不同**），是求和恰好相等的
巧合，不能当作"别名表示零成本"的证据。

## 7. 明确的限制（评审会问的）

1. **基准的"任务"是构造的，数据内容来自公开数据集**：6 个来源**全部是公开数据集**
   （SmartBench TDCS / PEC-Home / PrivacyLens / SimuHome / toolmem，许可见 `docs/06` §3），
   案例内容取自它们的真实记录；**敏感标识符是合成的 canary**（公开数据里不能放真 PII），
   问句在真实记录上模板化生成。**没有真实部署任务上的验证** —— 按 2026-10-17 的决定，
   这一条**不再追**，改为把公开数据集上的证据做扎实（逐来源拆解见 §3.6）。
2. **in-scope 对照覆盖 19/40**：其余 21 例的"目标区域本身 ≥512 token"，即**单个区域就
   装不进已发布方法的验证范围**。且 in-scope 切片同时在实体数（2 vs 6）与长度上不同，
   **不能把两者分离开**。
3. **`quito_x` 在 out-of-scope 只有 n=29/40**（11 例在最长案例上 OOM），`dac` 只有
   **15/40**（选择阶段超线性，见限制 9）—— 两者的 F1 都建立在**更容易的子集**上，
   **不可与其全量数字直接比较**。
4. **`alias_budget_link` 的主数字依赖"问题同步别名化"这个开关**：关掉时是 0.5397（Qwen）/
   0.5557（Mistral），打开后 Qwen **0.7450**、提示词层泄漏 **0/112**（作业 10602439）。
   **Mistral 尚未用该开关重跑** —— 第二个模型上只有"关"的 0.5557，这是仍然存在的缺口。
5. **`dac` 的 15/40 不能当"它失效"的证据**：它跑不完是**算力边界**（2.2k token 单例 1703 s），
   与"压缩破坏了实体标识"是两件不同的事。任何"`dac` 在这个任务上失效"的说法都不成立。
6. **cpc 的压缩器分词器在已发布版本间换过**（`cpc-1.0-llama-1b-tokenizer` →
   `cpc_tokenizer_compat`），其 `matched.text` 可能与已发布数字不同。
7. **1/112 个案例是退化的（基准缺陷）**：`longctx-toolmem-needle-0006` 的
   `anchor_kind = 'native'`（全库唯一一个），构建器把"锚点"设成了属性值本身，于是
   锚点与 gold 重合 —— 问题 `...for the entry describing BK789012?` 里**直接写着答案
   `BK789012`**，模型不读上下文就能答对。
   影响：它给**每个臂**都加 1/112 ≈ **+0.0089**，**均匀**，因此不改变任何排序或对比。
   发现方式：为"提问方式稳健性"写改写器时加的自检（`gold in question`）。
   → 待办：`anchor_kind='native'` 这条路径产出的案例应单独复核；报告里给出
   "含/不含该案例"两版数字（差异恒为 ±0.0089）。
8. **提问方式是模板化的**：已做**机械改写**（纯规则、不调用模型，无污染）生成两个变体
   （`data/longctx_paraA.jsonl` / `paraB.jsonl`，各 112 例，自检：gold 不因改写泄入问题）。
   稳健性检查**两个变体都跑完了**（§3.5）：核心对比 **+0.20（A）/ +0.25（原）/ +0.28（B）**，
   两个变体的 bootstrap Δ 都含 0；别名增益 **+0.14 / +0.23 / +0.26**，但变体 A 的
   bootstrap **不含 0**、变体 B **含 0** → **只能报这个区间，不能报"稳定"**。
9. **两个已发布方法无法在长上下文尺度上运行 —— 这是能力边界，不是表缺口**：

   | 方法 | in-scope（≤512 token） | out-of-scope（4k–18k） |
   |---|---|---|
   | `dac` | ✅ 19/19，8 秒/例 | ❌ **15/40**；2.2k token 上单例最慢 **1703 秒（28 分钟）**，6–18k 上 **>1.2 小时未完成一例**（CPU 侧选择超线性） |
   | `quito_x` | ✅ 19/19 | ❌ **29/40**；11 例在最长的上下文上 CUDA OOM（T5 在 18k token 上吃满 48/49 GB） |

   六个已发布方法里有**两个在长上下文尺度上根本跑不起来**（一个内存、一个算力）。
   这与 `docs/18` 的框架一致：这些方法从未被设计或验证于这个尺度。
   表中**不填假成绩**（遵循 batch1 `PROTOCOL.md` 的原则），只标注覆盖数。

10. **显存：配置敏感的 OOM，仍未完全定位（2026-10-17 又做了三次对照）**：
    - 已知：5 臂配置（5 prompt/例）在 V100 32GB 上稳定于 **gen 322** OOM，原问题与改写问题
      都会死（与改写无关）；9 臂 × 3 预算（21 prompt/例）在同一批 112 例上跑通；
      失败位次反推出肇事的是 ~9k token 的预算臂而非最长的 `full` 臂。
    - 新证据（三个诊断作业，日志见 `results/diag/oom_20261017/`）：把**最长的 3 个多实体案例**
      （18.2–18.3k token）单独抽成子集跑，`--batch 2` 与 `--batch 1` **都 OOM**，
      失败点都在 `torch.nn.functional.scaled_dot_product_attention`，请求 **34–35 GiB**
      （≈ 单个 18k 上下文的 fp32 注意力矩阵大小）。三次作业都落在
      `Tesla V100-PCIE-32GB / 32768 MiB`。
    - **与已完成作业直接矛盾**：`aliasq`（10602439）等 112 例作业**同样**在这张卡上、
      **同样**跑过这些案例 —— 同一批 18.2k/18.7k token 提示词留下了
      `pred='vacation_away'` / `'UNKNOWN'` 这类**真实生成结果**（非 stub、非空），
      `prompt_tokens` 记录为 18259 / 18695。同样代码、同样卡型，全量跑通、子集必 OOM。
    - **我不能解释这个差异**，所以只写事实：全量 112 例配置是可复现的（三次作业都跑通），
      **"只挑最长案例"的子集配置不可用**。今后长上下文作业**不要**用长案例子集，
      要么用全量案例文件，要么换 ≥48GB 的卡。
    - 顺带结论：**极小预算（0.10 / 0.15）本身不触发问题** —— 2 个 needle 案例上
      `RC=0`、预算对账通过；但多实体案例上的极小预算曲线因此**仍未测**，
      论文里不写这部分（缺就是缺）。
    - 纪律提醒：失败作业的 `.out/.err` 一律留档（`results/diag/`），
      否则事后只能凭记忆描述失败。
