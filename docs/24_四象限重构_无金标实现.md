## 24.1 原实现的问题：压缩时用了金标答案

`code/longctx/e2e_longctx_r5full.py` 的预算臂在选择保留哪些单元时，用到了**金标答案**：

```python
golds = gold_texts(case)                       # ← 金标答案
def ans_of(units):
    return [any(norm(g) in norm(u) for g in golds) for u in units]

def order_fn(units, ans_flags):
    # 含答案的单元排到丢弃序最后 -> 最后才被删
    return [i for i in rank if not ans_flags[i]] + [i for i in rank if ans_flags[i]]
```

**后果**：
1. 方法不可部署——真实场景不知道答案在哪一行
2. 外部基线（LLMLingua / CPC / Quito-X）拿不到这个信息，**对比不公平**
3. 头条数字被高估

### 影响有多大（模型无关实测，400 例抽样）

统计「含答案的单元是否被保留」：

| 案例类型 | A 纯冗余 | **B 冗余 + 保护锚点行** | C 金标（现行）|
|---|---:|---:|---:|
| 多实体（multi_entity）| 46.3% | **45.3%** | 100% |
| needle | 3.0% | **3.0%** | 100% |

**关键发现：保护锚点那一行，几乎救不了答案。**

因为锚点行和答案行不是同一行（同 unit 比例：多实体 0%、needle 34.6%）：

```
Account ID: ACCT-fc668719b347                          ← 锚点行（现行 link 臂保住的）
{"device": "media_player", "id": "..._0226_00", ...}   ← 答案行（仍被冗余规则删掉）
```

### needle 为什么只有 3%

答案（如 `multi_user_preferences`）在**大量干扰记录中重复出现**。在「哪行最重复就先删」的规则下，
**含答案那一行看起来最冗余，第一个被删**。

> **冗余度启发式与「含答案」是负相关的**：越像答案的记录越显得冗余。

所以在没有金标的情况下：

| 配置 | 答案保留 | 结果 |
|---|---|---|
| 只有冗余度（`budget_cluster`）| 46% / 3% | 接近随机 |
| 冗余 + 锚点行保护（`budget_cluster_link`）| 45% / 3% | **仍然大跌** |
| 冗余 + 保护整个 entry（`quad4`）| **100% / 100%** | 应接近现行水平 |
| 冗余 + 金标（原实现）| 100% / 100% | 但不可部署 |

即：**必须保护整个 entry，而 quad4 正是这么做的，且只用问题里的实体。**

## 24.2 新设计：用「问题点名实体所在的 entry」定义相关性

关键观察（在 2,728 例上实测）：

| 案例类型 | 数量 | 答案与锚点**同一 entry** | 同一行 |
|---|---:|---:|---:|
| 多实体 | 1,500 | **100.0%** | 0.0% |
| needle | 1,228 | **99.7%** | 34.6% |

数据集结构是：一条 `----- entry N -----` 记录里既有账号标识，也有该账号的 persona 记录。
问题点名了账号，因此**账号所在的 entry 就是相关区域，答案必然在其中**。

这个相关性**完全来自问题**（问题里就写着目标实体），不需要金标：

- 多实体：锚点 = `target_entity`（账号 ID，问题里点名）
- needle：锚点 = `anchor`（记录 ID，问题里点名）

### 四象限的四个操作

| 象限 | 操作 | 理由 |
|---|---|---|
| 敏感 + 相关 | **别名**（`[ACCOUNT-X]`）| 既脱敏又保留指代 |
| 敏感 + 不相关 | **删除**（整单元丢弃）| 与任务无关，没必要留 |
| 不敏感 + 相关 | **保留** | 含答案/上下文 |
| 不敏感 + 不相关 | **按冗余度填充**至预算 | 压缩空间 |

实现为 `code/longctx/e2e_quad.py` 的 `quad4` 臂（由 `make_e2e_quad.py` 从原脚本生成，评测管线一字未改）。

## 24.4 对照臂 `quad4_del`：检验"别名 vs 删除"

`quad4_del` 与 `quad4` 唯一差别：**(敏感, 相关) 这一格用删除而不是别名**。

模型无关预测（已实测输出结构）：

| 臂 | 类型 | 答案在输出 | 锚点在输出 |
|---|---|---:|---:|
| `quad4` | 多实体 | 100% | **100%** |
| `quad4` | needle | 100% | 100% |
| `quad4_del` | 多实体 | 100% | **0%** |
| `quad4_del` | needle | 100% | 100% |

原因：多实体的锚点是**账号 ID（敏感值）**，删除后指代断裂；needle 的锚点是**记录 ID（非敏感）**，删除不影响。

**因此预测**：`quad4_del` 在多实体上大跌、在 needle 上接近 `quad4`。
若成立，就直接证明「敏感且相关这一格必须用别名而非删除」。

## 24.6 对论文的影响（待 F1 确认）

如果实测符合预测：

> 方法本身成立，但实现必须从「用金标答案选行」改为「保留问题点名实体所在 entry」；
> 并且「敏感且相关」这一格必须用别名，不能用删除。
> 前者消除不可部署性，后者有 `quad4` vs `quad4_del` 的干净对照支撑。

这意味着论文**不需要推翻方法**，需要改的是：
1. 方法描述里"相关性"的定义（金标 → 锚点所在 entry）
2. 主结果表必须用无 oracle 的版本重跑
3. 与外部基线的对比必须双方都无 oracle（改后即满足）
