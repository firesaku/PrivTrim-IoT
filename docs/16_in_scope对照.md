# 16 · in-scope 对照：把多实体任务压进已发布方法的验证范围

> 2026-10-17 ｜ 目的：回答复查提出的 M1 —— 已发布方法只在 ≤512 token 上验证过
> （其 96 个案例 186–430 token，**没有一例超过 512**），而 longctx 是 4k–18k。

---

## 1. 一个结构性的硬约束

`PROTOCOL.md` 要求"上下文完整装入 Provence 的 512-token 窗口"。但一个实体区域约
1300 字符 ≈ 400 token，因此 **512 token 装不下 6 实体任务**。能在 in-scope 尺度上
表达的最大规模是 **2 个实体**。

所以这个对照的口径必然是：

| | 实体数 | 上下文 |
|---|---|---|
| in-scope | **2** | **≤512 token** |
| out-of-scope（longctx） | 6 | 4k–18k token |

两者**同时**在实体数与长度上不同。**这是窗口大小的硬约束，不是设计选择**，所以本对照
只能回答"在它们自己的尺度上、一个更小规模的多实体消歧还成不成立"，
**不能单独把长度与实体数分离开**。论文里必须这么说。

## 2. 切片怎么造（以及第一版为什么被推翻）

对每个 multi_entity 案例：
1. **目标窄窗**：以目标实体偏移与 gold 偏移为中心各留 260 字符，裁到目标区域内 →
   必然同时含目标实体与 gold；
2. **干扰窄窗**：另取一个在原文中出现的实体值，同样开窗并裁到它所属区域 → 含第二个实体；
3. 拼接后把预算约束**只施加在干扰段上**（`prefix_budget` 是砍尾的，不能让裁剪碰到目标段）。

**第一版被推翻的经过**：第一版直接取"整个目标区域 + 一个干扰区域"再裁到 512。
结果 25 例里**只有 2 例**真的含 ≥2 个实体 —— 一个区域本身就 400–3700 token，
目标区域单独就把预算占满、干扰区域被裁成空串。那些切片其实是**单实体 needle 题**，
元数据却写着 `n_entities=2`。若不查这一步，就会把"已发布方法在 in-scope 上也失效"
写成结论，而证据是错的任务类型。

→ 教训：**切片的元数据声明必须由切片内容本身验证**，不能由构造意图决定。
现在切片生成后有一道独立自检：`≤512` 且 `≥2 个实体值在文本中` 且目标实体在 且 gold 在，
不通过就丢弃。最终 **19/40** 例通过（21 例丢弃：目标窗口单独就 ≥512，塞不下干扰实体）。

## 3. 结果（19 例，2 实体，≤512 token，50% 预算 ≈ 256 token）

### 3.1 目标位置的影响 —— 机制被受控实验证实

我先把目标段放在**尾部**（保持原文顺序），发现 `provence`/`cpc` 的实体存活率
（0.21 / 0.58）**低于** out-of-scope（0.80 / 0.90）。这不合理，所以做了第二个变体：
把目标段放到**首部**，其余不变。

| 方法 | 实体存活（目标在后，中位位置 0.69） | 实体存活（目标在前，中位位置 0.16） |
|---|---:|---:|
| `full` | 1.00 | 1.00 |
| **`provence`** | **0.21** | **0.74** |
| **`cpc`** | **0.58** | **0.79** |
| `llmlingua2` | 0.95 | 1.00 |
| `quito_x` | 1.00 | 1.00 |
| `mask_llmlingua2` | 0.00 | 0.00 |
| `dac` | 0.00 | 0.00 |

**移动目标位置就把 provence 从 0.21 拉到 0.74** —— 所以 in-scope 的崩塌是
**裁剪位置**造成的，不是上下文长度。发布的 `prefix_budget` 是**砍尾**的，
预算紧时尾部内容先被牺牲。

这条在真实基准上同样成立：longctx 案例里目标区域就在文末
（实测 `target_region_start/end = 6296/7625`，而 `context` 长 7627 字符）→
**尾部裁剪系统性地先切目标区域**。只是在 18k 上预算宽裕（9k token 对一个 400 token
的区域），所以 237 个 (案例, 方法) 对里一次都没切到答案（先前实测 `KILLED_BY_ADAPTER = 0`）。

### 3.2 新发现：预算紧时压缩器会把标识符**改坏**，而不是删掉

| 方法 | in-scope 完好 / 改坏 / 丢失 | out-of-scope 完好 / 改坏 / 丢失 |
|---|---:|---:|
| `full` | 100% / 0% / 0% | 100% / 0% / 0% |
| `quito_x` | 100% / 0% / 0% | 100% / 0% / 0% |
| `llmlingua2` | 95% / 5% / 0% | 98% / 0% / 2% |
| `cpc` | 58% / 5% / 37% | 90% / 0% / 10% |
| **`provence`** | **21% / 26% / 53%** | 80% / 0% / 20% |
| `mask_llmlingua2` | 0% / 0% / 100%（设计如此，脱敏） | 同 |
| `dac` | 0% / 0% / 100% | 0% / 0% / 100% |

**`provence` 在 26% 的 in-scope 案例上把实体串改坏**——既没保住也没干净删除。
实例（`dac`）：

```
原文：Account ID: ACCT-9a6ffa50f962
输出：Account ID: ACCTaffa
```

对一篇隐私论文来说，这**比删除更危险**：`ACCTaffa` 是**看起来合法的假标识符**，
可能与另一个真标识符撞上（collision），而下游系统无法察觉。

注意这是**下界**：分类器要求原始串有 8–12 字符的连续片段残留才算"改坏"，
所以 `dac` 那种更碎的破坏被归到"丢失"里了。真正的改坏率高于表中数字。

## 4. 对论断的影响

1. **不能说"它们只在长上下文上失效"** —— in-scope 同样失效，甚至更凶。
   正确的表述是：失效由 **预算与"实体→属性绑定跨度"之比**决定，
   而不是由绝对上下文长度决定。50% 的 512 token 与 50% 的 18k token 都会触发，
   前者因为绑定跨度占预算比例更大而更严重。
2. **"它们被推到验证范围之外"这个框架（M1）需要修正**：在它们自己的范围里、
   按同一 50% 预算口径，同样的问题就出现了。这对我们的论断是**加强**，不是削弱——
   说明这不是"没适配好长上下文"，而是**冗余度信号与实体标识的根本冲突**。
3. **改坏（corruption）是一个独立的、可发表的失效模式**，且是隐私相关的：
   压缩器输出的假标识符看起来合法。删除至少是诚实的不确定性；改坏不是。

## 5. 仍未做

- in-scope 切片的**模型打分**（F1）还没跑。模型无关的三列已经足够说明机制，
  但论文里 `[2]` 主表需要 in-scope 的 F1 才能与 out-of-scope 并列。
- `dac` 的改坏率需要更细的分类器（按字符级编辑距离，而不是固定长度片段）。
- 19/40 的覆盖率要在论文里写明：剩下 21 例的"目标区域本身 ≥512 token"，
  即**单个区域就装不进已发布方法的验证范围**。
