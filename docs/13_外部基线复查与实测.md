## 1. 被推翻的假设：512 不是"只看开头 512 token"

我原来的担心是：quito_x(T5) / provence(DeBERTa) / llmlingua2(xlm-R) 的窗口都是 512，
而我们的上下文 4k–18k，所以它们可能**只按前 512 token 决策、其余原样返回**。如果真是
这样，"基线失效"就是我的适配器造成的假象。

复查从源码给出了机制：两者的 `__chunk_context` / `sent_split_and_tokenize` 都是
**遍历全文切块**（`while st < n`），硬截断分支因块已 ≤510 而**不触发**。限制是
**块间无注意力**，不是头部截断。

然后我用一条**零成本判据**（只用已存产物里的 `trials`）终审：

| 方法 | max_trial_tokens / original_tokens | rate≈1 时吐出 |
|---|---:|---:|
| `llmlingua2` | **0.996** | 6078 token |
| `dac` | 0.993 | 2217 token |

rate 趋近 1 时必须能吐出接近全文的量 —— 实测正是如此。**假设被证伪。**

这条很重要，因为它把结论的**表述**改了：不能说"基线只看了前 512 token"（假的），
只能说"感受野 512、跨块不可关联"，而这对多跳/多实体题是真限制（锚点与目标实体常跨块）。

## 2. 复查抓到的四个 critical，以及我核实后的处理

### C1 换模型时 token 口径断裂 —— **确认为真，已规避**

`ext_compress.py` 用 `C.get_tokenizer()`（batch1 硬编码 Qwen2.5-7B），而 harness 的
`nt()` 随 `--lm` 变。Qwen 作业下两者是同一快照哈希所以无问题；但 **Mistral 作业下
基线按 Qwen 计数、harness 按 Mistral 计数**，实测同一批案例 Qwen 最长 18608、
Mistral 19838（+6.6%），9k 预算上差约 600 token。

→ 处理：外部基线**只与 Qwen 搭配**；Mistral 作业不含 ext 臂。这一点必须写在论文里，
否则复现者会踩。

### C2/C3 空文件与失败方法会静默消失 —— **确认为真，已修**

- 原 `patch_ext_arms.py` 在 JSONL 为空时一条 ext 臂都不注入，报告与"根本没做外部对比"
  无法区分；`cells.json` 也不记录 ext 出处。
- 上游 `ext_compress.py` 在 `load_method` 失败时写个没人读的 txt 就 `continue`，该方法
  **连目录都没有** → 从对比里彻底消失。

→ 处理：新增 `ext_to_arms.py`，**失败也出行**（`status=error` 并带 error 文本），
并携带 `trim / original_tokens / target_tokens / code_sha / warnings`。
实测产出 444 行，其中 **11 行是 error 行且被保留**（quito_x），没有静默丢失。

### C4 决定公平性的裁剪量进不了对比表 —— **机制为真，但实测影响为零**

`compress.py` 用 `prefix_budget` 把超预算的输出**从尾部裁到恰好等于预算**，所以
`matched.tokens` 被钉死在 target 上 —— **`[1]` 表的 `fill=100%` 是裁剪造成的，
不是"公平匹配"的证据**，该表在结构上不可能发现这个偏差。

实测裁剪量（40 例 multi_entity）：

| 方法 | 裁剪 p50 | 裁剪 max |
|---|---:|---:|
| `provence` | **102** | **2657** |
| `cpc` | **60** | **2982** |
| `mask_llmlingua2` | 25 | 248 |
| `llmlingua2` | 20 | 223 |
| `quito_x` | 3 | 20 |

裁剪量**与方法高度相关**（provence/cpc 被砍一两个数量级更多）。

**但关键的反证**：`compress_case` 已经把裁剪前的文本存进了 `adapter_source`，所以我
直接算了"答案是不是被我们砍掉的"：

| 方法 | gold 在裁剪前 | gold 在裁剪后 | **被我们砍掉** |
|---|---:|---:|---:|
| `provence` | 37/41 | 37/41 | **0** |
| `cpc` | 35/41 | 35/41 | **0** |
| `mask_llmlingua2` | 34/41 | 34/41 | **0** |
| `llmlingua2` | 31/41 | 31/41 | **0** |
| `quito_x` | 22/30 | 22/30 | **0** |
| `full`（未压缩） | 41/41 | 41/41 | **0** |

**237 个 (案例, 方法) 对里，一次都没砍到答案。** 机制存在，本次影响为零 ——
这个结论只有在算过之后才敢说。

### 另一条方向相反的小问题（m4）：基线实际拿到的 token 比内部臂多

内部预算臂 0.5 档实测 fill 只有 **92–93%**（r3: target_mean 3982.1 / achieved 3659–3709），
而 ext 臂被裁剪钉在 **100%** → **基线多得约 7% token**。

方向**对基线有利**，即对我们的论断是保守的。论文里要主动写出来，预防"你把基线饿死了"。

## 3. 不依赖模型的核心结果

50% 预算、40 个多实体案例，只看"答案串还在不在上下文里"（模型无关的上界）：

| 臂 | gold 存活率 |
|---|---:|
| 未压缩 `full` | **100%**（41/41） |
| `provence` | 90%（37/41） |
| `cpc` | 85%（35/41） |
| `mask_llmlingua2` | 83%（34/41） |
| `llmlingua2` | **76%**（31/41） |
| `quito_x` | 73%（22/30） |

而本项目的 `budget_cluster_link` 在 r3 上 `gold_in_ctx = 100%`（112/112）。
**这一列完全不需要跑模型**，是"冗余度选择器会把答案挤掉"的最干净证据。

位置覆盖率（输出落在原文 10 个位置等份中的分布）：

| 方法 | deciles 覆盖 | frac_d0 | at_gold | 只覆盖 1 段的案例 |
|---|---:|---:|---:|---:|
| `full`（恒等，仪器自检） | 8.93 | 9.5% | 7.9% | 0 |
| `provence` | 7.20 | 10.9% | 10.5% | 1 |
| `cpc` | 7.07 | 15.2% | 12.3% | 0 |
| `llmlingua2` | — | 21.7% | 28.2% | 9 |
| `quito_x` | 4.40 | 5.2% | **4.6%** | 9 |

`full` 的 8.93 而非 10.0 是度量本身的噪声底（分句与加权造成的），所有方法要相对它读。
`quito_x` 的 `at_gold=4.6%` 明显低于其他方法：它保留的内容极少落在答案所在区段。

## 4. 计算可行性：两个方法没跑完，而这本身是发现

| 方法 | 成功 | 失败 | 失败原因 |
|---|---:|---:|---|
| `provence` / `cpc` / `llmlingua2` / `mask_llmlingua2` / `full` | 41/41 | 0 | — |
| `quito_x` | 30/41 | **11** | 长案例上 CUDA OOM（T5 在 18k token 上把 48/49 GB 吃满） |
| `dac` | 2/41 | 39 | `load_method` 时 CUDA OOM（前一个方法残留显存） |

两点必须如实处理：

1. **quito_x 的 11 例失败集中在最长的案例上** → 它只在较短案例上被评到，
   这是**选择偏差**，不是"它分数低"。要么单独说明，要么补跑（需分进程 + 更小批）。
2. `dac` 的 OOM 是**我的跑法**造成的（同一进程内依次加载 6 个方法，显存未释放），
   不是 dac 本身不可用。修法：每个方法独立进程。**这条不修就不能说 dac 失败。**

## 5. 复查还指出的一条框架性问题（M1）：已发布协议自己划了边界

`PROTOCOL.md:15` 明文要求「增强上下文与问题必须**完整装入 Provence 的 512-token 窗口**，
所有方法处理同一完整上下文，**无静默截断**」。实测 batch1 的 96 个案例
`original_tokens`：min 186 / p50 234 / max 430，**>512 的 0/96**。

也就是说：**已发布结果从未在 512 以上验证过**，而 longctx 是 4k–18k，约为已验证
上限的 **36–43 倍**。

这不改变结论，但改变**表述的合法性**：
- 不能说"已发布方法在这个任务上失效"；
- 只能说"我们把它们推到其协议验证范围之外，在那里它们丢答案；在协议范围内
  （≤512 token 切片）它们是否仍失效，是另一个必须单独做的实验"。

→ 待办：加一个 **in-scope 对照切片**（同源、上下文 ≤512 Qwen token），让两臂都跑。
它同时给出管线锚点校验（在已发布尺度上应复现已发布的相对排序），把"长上下文退化"
和"适配器伪影"分开。这是补上 M1 的唯一正路。
